# LabApp Specification

Status: v0.1, business rules approved. This document is the source of truth for behavior. The OpenAPI contract generated by the backend must match it. Field limits and messages are defaults and may be adjusted by changing this file first.

## 1. Scope

An order-to-cash mini-ERP: customers, a read-only seeded product catalog, orders, invoices and payments. The screen language is Spanish; the currency is USD. Code, identifiers and API field names are in English.

## 2. Roles and permissions

Four seeded users, one per role, all sharing one demo password that the login screen displays. The API identifies the roles with the values `admin`, `sales`, `finance` and `readonly`.

| Role | Seeded user |
|---|---|
| Admin | `admin@labapp.test` |
| Sales | `sales@labapp.test` |
| Finance | `finance@labapp.test` |
| Read-only | `readonly@labapp.test` |

| Action | Admin | Sales | Finance | Read-only |
|---|---|---|---|---|
| View customers, products, orders, invoices, payments | yes | yes | yes | yes |
| Create, edit, deactivate and reactivate customers | yes | yes | no | no |
| Create and edit Draft orders | yes | yes | no | no |
| Confirm, cancel and mark orders as Shipped | yes | yes | no | no |
| Create invoices | yes | no | yes | no |
| Register payments | yes | no | yes | no |
| Change the tax rate | yes | no | no | no |

The server enforces every permission. A forbidden action returns HTTP 403 with code `FORBIDDEN` and the message "No tienes permiso para realizar esta acción." The UI may hide or disable controls, but never replaces the server check.

## 3. Authentication and sessions

- `POST /api/auth/login` takes `{email, password}`. The email is trimmed and lowercased before lookup. On success it returns 200 with the user (`id`, `name`, `email`, `role`) and sets the session cookie `labapp_session` (HttpOnly, SameSite=Lax, Secure over HTTPS).
- `POST /api/auth/logout` ends the session and returns 204. `GET /api/auth/me` returns the current user.
- A session expires after 8 hours without activity (sliding window), measured with the application clock, so `SESSION_EXPIRED` can be tested by moving the clock. Only `POST /api/auth/login`, `POST /api/auth/logout` (which is idempotent: it ends the session if there is one and answers 204 either way) and `GET /api/health` work without a session.
- An unknown email and a wrong password return the same error, so accounts cannot be enumerated.
- State-changing requests (POST, PUT, PATCH, DELETE) that carry an `Origin` header must match the application origin, otherwise the server answers 403 `CSRF_ORIGIN_MISMATCH`. The application origin is the `APP_ORIGIN` setting (online, the origin of each deployment, that is `https://` plus the platform variables `VERCEL_URL`, `VERCEL_BRANCH_URL` and `VERCEL_PROJECT_PRODUCTION_URL` when they are set, is allowed too, because preview URLs change with every deployment) (for example `http://localhost:3000` locally and the Vercel URL online); the session cookie is `Secure` when `APP_ORIGIN` starts with `https://`. Requests without `Origin` (API clients and test suites) are allowed because the cookie is SameSite=Lax. An API suite authenticates by calling the login endpoint and reusing the cookie.
- Rate limits apply only when `TEST_MODE=0`: 120 requests per minute and 10 login attempts per minute per client IP. Exceeding a limit returns 429 `RATE_LIMITED` with a `Retry-After` header. A request with a valid test token is exempt even then. A valid test token is an `X-Test-Token` header equal to a non-empty `TEST_TOKEN`. The client IP is the `X-Forwarded-For` entry that is `TRUSTED_PROXY_COUNT` entries from the right (default 0: the socket address), so online visitors behind the proxies do not share one bucket.

| Situation | HTTP | Code | Message (es) |
|---|---|---|---|
| Wrong email or password | 401 | `INVALID_CREDENTIALS` | Email o contraseña incorrectos. |
| No session | 401 | `UNAUTHENTICATED` | Inicia sesión para continuar. |
| Session expired | 401 | `SESSION_EXPIRED` | Tu sesión expiró. Inicia sesión de nuevo. |
| Origin mismatch | 403 | `CSRF_ORIGIN_MISMATCH` | La solicitud no proviene de la aplicación. |
| Too many requests | 429 | `RATE_LIMITED` | Demasiadas solicitudes. Espera un momento e inténtalo de nuevo. |

## 4. Customers (flow 1)

| Field | Rule |
|---|---|
| `name` | Required, 2 to 120 characters. |
| `email` | Required, valid format, unique (case-insensitive). |
| `phone` | Optional, 7 to 20 characters of digits, spaces, `+`, `-`, `(`, `)`. |
| `tax_id` | Optional, 3 to 30 letters, digits or hyphens. Required to issue an invoice. |
| `address` | Optional, up to 200 characters. May span several lines. |
| `status` | `active` or `inactive`. A new customer is `active`. |

Rules:
- Customers are never deleted. They are deactivated and can be reactivated.
- An inactive customer cannot be chosen for an order. Deactivating a customer does not change existing orders, but confirming a draft whose customer has become inactive fails with `CUSTOMER_INACTIVE`. A confirmed order of an inactive customer can still be invoiced and paid, and a paid one can still be shipped.
- Field-level problems return HTTP 422 `VALIDATION_ERROR` with one entry per field.
- The email is trimmed and lowercased before validation and uniqueness checks.

| Situation | HTTP | Code | Message (es) |
|---|---|---|---|
| Email already used | 409 | `CUSTOMER_EMAIL_TAKEN` | Ya existe un cliente con ese email. |
| Creating, editing or confirming an order for an inactive customer | 422 | `CUSTOMER_INACTIVE` | El cliente está desactivado y no puede recibir pedidos. |
| Invoice for a customer without `tax_id` | 422 | `CUSTOMER_TAX_ID_REQUIRED` | El cliente necesita un ID fiscal para poder facturar. |

### Customers API

Every route needs a session. Reading is open to every role; creating, editing, deactivating and reactivating need the customer-management permission (Admin and Sales, SPEC section 2), otherwise 403 `FORBIDDEN`.

| Request | Purpose | Answer |
|---|---|---|
| `GET /api/customers` | List, with the query parameters below | 200 `{items, page, page_size, total}` |
| `POST /api/customers` | Create | 201 `Customer`, `Location: /api/customers/{id}` |
| `GET /api/customers/{id}` | Read one | 200 `Customer` |
| `PATCH /api/customers/{id}` | Partial update; the body must carry `version` | 200 `Customer` |
| `POST /api/customers/{id}/deactivate` | Set the status to `inactive` | 200 `Customer` |
| `POST /api/customers/{id}/reactivate` | Set the status to `active` | 200 `Customer` |

`Customer` is `{id, name, email, phone, tax_id, address, status, version, created_at, updated_at}`. Optional fields are `null` when empty. Timestamps are ISO 8601 in UTC with a trailing `Z`. Every response that returns one customer also carries `ETag: "<version>"`.

Rules:
- **Create.** `name` and `email` are required: an empty or whitespace-only value is `REQUIRED`, and a missing one is reported together with every other problem. Text fields are trimmed, and an empty optional field is stored as `null`. The email is also lowercased. Limits and formats are those of the field table above. Each field reports only the first check that fails, in this order: required, character set or format, minimum length, maximum length (so `"abc"` as a phone is `INVALID_FORMAT`, not `TOO_SHORT`). A control character, NUL included, in any text value is `INVALID_FORMAT`, with one exception: `address` may contain line breaks (`\n` or `\r\n`, stored as `\n`), because it is entered in a multi-line field. A lone `\r` and every other control character are still `INVALID_FORMAT`, and the 200-character limit counts the stored text. `phone` and `tax_id` accept ASCII only, as the field table says; `name` and `address` accept any other characters. A valid email has no whitespace, one `@`, a non-empty local part, a domain of at least two non-empty labels separated by dots, and at most 254 characters. A new customer has `status` `active`, `version` 1 and `updated_at` equal to `created_at`. An unknown field in the body is a 422 `INVALID_FORMAT` on that field.
- **Update.** Only the fields present in the body change. `version` is required (`REQUIRED` on `version` when missing) and is an integer from 1 to 2147483647 (otherwise `OUT_OF_RANGE` on `version`). An unknown field in the body is a 422 `INVALID_FORMAT` on that field. `null` clears `phone`, `tax_id` and `address`; `null` for `name` or `email` is `REQUIRED`. An email already used by another customer is 409 `CUSTOMER_EMAIL_TAKEN`. A stale `version` is 409 `VERSION_CONFLICT`. A request that changes nothing answers 200 and leaves `version` and `updated_at` as they were; a request that changes something increases `version` by 1 and sets `updated_at`.
- **Deactivate and reactivate.** They accept an optional `If-Match: "<version>"`; a malformed value is a 422 `INVALID_FORMAT` on `If-Match`, and a stale one is 409 `VERSION_CONFLICT` even when the customer already has the requested state. Asking for the state the customer already has, with a current or absent `If-Match`, answers 200 with no change.
- **List.** `page` is an integer from 1 to 1000000 (a non-integer is 422 `INVALID_FORMAT` on `page`; any other value is 422 `OUT_OF_RANGE` on `page` with the message "El valor debe estar entre 1 y 1000000."); a page beyond the last one returns empty `items`. `page_size` is always 20. `q` is trimmed and ignored when empty; it has at most 100 characters (`TOO_LONG` on `q`) and no control characters (`INVALID_FORMAT` on `q`). It is literal text, never a pattern: `%`, `_` and `\` mean themselves. It matches customers whose name or email contains it, ignoring case and accents, where "ignoring case and accents" is defined as: Unicode NFKD, combining marks removed, case-folded, applied to both the text and `q`. `status` is `active` or `inactive` (otherwise 422 `INVALID_FORMAT` on `status`) and filters by status; without it every customer is listed. The order is `created_at` descending, then `id` descending. `total` counts every match, not only the current page.
- **Not found.** An unknown id, and any integer outside 1 to 2147483647, is 404 `NOT_FOUND`; an id that is not an integer is a 422 `VALIDATION_ERROR` on `id`. For routes with an id, the order of SPEC section 7 holds: permission, then existence (404), then body validation (422), then the version.
- **Seed.** The ten customers of `docs/SEED.md` exist from the start, with `version` 1 and `updated_at` equal to `created_at`.

## 5. Orders (flow 2)

States: `draft`, `confirmed`, `paid`, `shipped`, `cancelled`.

| Transition | Allowed from | Who | Effect |
|---|---|---|---|
| Create | none | Admin, Sales | New `draft` with number `PED-0001`, `PED-0002`, ... |
| Confirm | `draft` | Admin, Sales | Checks stock, decrements it, freezes the tax rate and totals. |
| Pay | `confirmed` | Set by a successful payment (section 6) | Order becomes `paid`. |
| Ship | `paid` | Admin, Sales | Order becomes `shipped`. |
| Cancel | `draft`, `confirmed` | Admin, Sales | A confirmed order gets its stock back and its invoice voided. |

Any other transition returns HTTP 409 `INVALID_TRANSITION`: "No se puede pasar el pedido de {from} a {to}."

Products are read-only and come from the seed: `id`, `sku` (unique, up to 20 characters), `name` (up to 120), `price` (`NUMERIC(12,2)`, greater than 0) and `stock` (integer, 0 or more).

Lines:
- An order has a customer (active) and up to 10 lines, at least 1 to be confirmed. Each line has a product and an integer quantity from 1 to 999. The cap is below the 15 seeded products so that it can be reached.
- A product appears at most once per order. Adding it again returns `ORDER_DUPLICATE_PRODUCT`.
- The unit price is copied from the product when the line is added.
- Only a `draft` order can be edited.
- A draft can be saved with no lines; `ORDER_EMPTY` applies only when confirming.
- The customer of a draft can be changed while it is a draft; the new customer must be active.
- `shipped` and `cancelled` are final. A `paid` order can only move to `shipped`.

Totals (computed on the server):
- `subtotal` = sum of quantity times unit price.
- `tax` = `subtotal` × `rate` ÷ 100, rounded half-up to 2 decimals (a tie such as 5.025 becomes 5.03, where half-even would give 5.02).
- `total` = `subtotal` + `tax`.
- The tax rate is a percentage set by Admin (default 10.00, range 0.00 to 100.00, up to 2 decimals). A draft shows the current rate as a preview; the rate is frozen in the order when it is confirmed or cancelled. A reset restores the rate to `DEFAULT_TAX_RATE` (10.00 unless the environment says otherwise); the seed totals assume 10.00.

| Situation | HTTP | Code | Message (es) |
|---|---|---|---|
| Product repeated in the order | 422 | `ORDER_DUPLICATE_PRODUCT` | Ese producto ya está en el pedido; edita su cantidad. |
| More than 10 lines | 422 | `ORDER_TOO_MANY_LINES` | Un pedido admite como máximo 10 líneas. |
| Confirm without lines | 422 | `ORDER_EMPTY` | El pedido debe tener al menos una línea. |
| Edit a non-draft order | 409 | `ORDER_NOT_EDITABLE` | Solo se puede editar un pedido en borrador. |
| Not enough stock on confirm | 409 | `INSUFFICIENT_STOCK` | No hay stock suficiente de {product}: disponible {available}, solicitado {requested}. |
| Stale `version` on update | 409 | `VERSION_CONFLICT` | El registro cambió mientras lo editabas. Recarga e inténtalo de nuevo. |

Concurrency:
- Every versioned record (customer, order, invoice) has an integer `version`, starting at 1 and increasing by 1 on every change. Responses include `version` and an `ETag` header holding it (for example `"3"`).
- **Transport.** `PATCH` requests must include `version` in the body; a missing value is a `VALIDATION_ERROR` with `REQUIRED` on `version`. Transition requests (confirm, cancel, ship, invoice, pay) have no body and may send `If-Match: "<version>"`. The version checked is that of the main resource of the endpoint: the order for confirm, cancel, ship and invoice, and the invoice for pay. A stale value returns 409 `VERSION_CONFLICT`; an absent value skips the version check.
- **Locking.** Every mutation of an order, whether a transition or an edit of its lines or customer, locks the order row first (`SELECT ... FOR UPDATE`), then its invoice, then the customer row (`FOR SHARE`, so a concurrent edit of the customer's `tax_id` cannot race the invoice snapshot), then the affected stock rows in ascending product id order. The `version` and the state are checked after locking, never before. This prevents overselling, deadlocks and races such as cancelling an order while its payment is being approved: the transaction that locks the order second sees the new state and fails with `INVALID_TRANSITION` or `INVOICE_NOT_PAYABLE`. A lock wait longer than 5 seconds returns 503 `LOCK_TIMEOUT`.
- Confirming is all-or-nothing. If several lines lack stock, the response lists every short line in `shortages[]` (`product_id`, `sku`, `name`, `available`, `requested`), ordered by product id, and the message names the first one.
- **Double submit.** Because the version is checked under the lock, a repeated transition behaves the same whether it arrives one after the other or at the same time: with a `version` (`If-Match`) the second request returns `VERSION_CONFLICT`, and without one it returns `INVALID_TRANSITION`. The UI avoids both by disabling the control while the request runs (`aria-busy`).

### Orders API

Every route needs a session. Reading (orders and products) is open to every role. Creating an order, changing its customer and adding, editing or removing lines need the permission to edit draft orders; confirming, cancelling and shipping need the permission to transition orders (both are Admin and Sales, section 2); changing the tax rate is Admin only. Anything else is 403 `FORBIDDEN`.

Money in JSON is a string with exactly 2 decimals (`"19.90"`), never a number; the tax rate is a string with 2 decimals (`"10.00"`). Ids and quantities are integers. Timestamps follow section 4 (UTC with a trailing `Z`).

| Request | Purpose | Answer |
|---|---|---|
| `GET /api/products` | The whole catalog, ordered by `id`; no paging | 200 `{items: [Product]}` |
| `GET /api/settings` | Current settings (every role) | 200 `{tax_rate}` |
| `PATCH /api/settings` | Change the tax rate (Admin) | 200 `{tax_rate}` |
| `GET /api/orders` | List, with the query parameters below | 200 `{items: [OrderSummary], page, page_size, total}` |
| `POST /api/orders` | Create a draft: `{customer_id}` | 201 `Order`, `Location: /api/orders/{id}` |
| `GET /api/orders/{id}` | Read one | 200 `Order` |
| `PATCH /api/orders/{id}` | Change the customer of a draft: `{customer_id, version}` | 200 `Order` |
| `POST /api/orders/{id}/lines` | Add a line: `{product_id, quantity, version}` | 201 `Order` |
| `PATCH /api/orders/{id}/lines/{line_id}` | Change a quantity: `{quantity, version}` | 200 `Order` |
| `DELETE /api/orders/{id}/lines/{line_id}` | Remove a line; optional `If-Match` | 200 `Order` |
| `POST /api/orders/{id}/confirm`, `/cancel`, `/ship` | Transitions; no body; optional `If-Match` | 200 `Order` |

Shapes:
- `Product` is `{id, sku, name, price, stock}`; `stock` is live (it changes when orders are confirmed or cancelled).
- `OrderSummary` is `{id, number, status, customer_id, customer_name, line_count, total, version, created_at, updated_at}`.
- `Order` is `{id, number, status, customer: {id, name, status}, lines: [OrderLine], subtotal, tax_rate, tax, total, invoice_id, version, created_at, updated_at}`. `OrderLine` is `{id, product_id, sku, name, quantity, unit_price, line_total}` (`line_total` is quantity times unit price). Lines are ordered by `id`. `invoice_id` is `null` until the order has an invoice (section 6). While the order is a `draft`, `tax_rate` is the current rate and the totals are computed on every read; from the moment it is confirmed or cancelled they are the frozen values. Every response that returns one order also carries `ETag: "<version>"`, and every change to the order, including each line change, increases its `version` by 1 and sets `updated_at`.
- A new draft has no lines, `subtotal`, `tax` and `total` of `"0.00"`, `version` 1 and `updated_at` equal to `created_at`. Its number is the next one of the `PED` sequence (`format_number("PED", n)`), taken inside the same transaction as the insert.

Rules:
- **Create.** `customer_id` is required (`REQUIRED`), an integer (`INVALID_FORMAT`), must exist (`REFERENCE_NOT_FOUND` on `customer_id`) and the customer must be active (422 `CUSTOMER_INACTIVE`). An unknown field in any body is a 422 `INVALID_FORMAT` on that field.
- **Edit.** Only a `draft` can be edited (`ORDER_NOT_EDITABLE`). The customer of the draft must be active at the time of every edit (`CUSTOMER_INACTIVE`); the one exception is changing the customer, where only the **new** customer must be active and the status of the old one is irrelevant. A request that changes nothing (the same customer, the same quantity) answers 200 with the order untouched: no new `version`, no new `updated_at`; it is decided after the version, editability and customer-active checks, so a stale `version`, a non-draft order or an inactive customer still fails first. `version` is required in the bodies that carry it (`REQUIRED`) and is an integer from 1 to 2147483647 (otherwise `OUT_OF_RANGE`). The `field` of a body error is exactly one of `customer_id`, `product_id`, `quantity`, `version` and `tax_rate` (never a path such as `lines[0].quantity`); the only exceptions are an unknown field of the body, whose own name is the `field` (`INVALID_FORMAT`), and a body that is not a JSON object, whose `field` is `body`. Errors that can be found from the request alone (required, type, range) are reported together; an unknown `product_id` or `customer_id` (`REFERENCE_NOT_FOUND`) is looked up only when there are none of those. Integers are strict: `"5"`, `5.0` and `true` are `INVALID_FORMAT`. A `customer_id` or `product_id` in a body outside 1 to 2147483647 is `REFERENCE_NOT_FOUND`. Adding a line: `product_id` is required and must exist (`REFERENCE_NOT_FOUND` on `product_id`), `quantity` is an integer from 1 to 999 (`INVALID_FORMAT`, `OUT_OF_RANGE`), the unit price is copied from the product at that moment, a product already in the order is `ORDER_DUPLICATE_PRODUCT` and an 11th line is `ORDER_TOO_MANY_LINES`. Changing a quantity keeps the unit price of the line. A `line_id` that does not belong to the order is 404 `NOT_FOUND`. Stock is not checked when editing, only when confirming.
- **Transitions.** They follow the table above. A transition that the state does not allow is 409 `INVALID_TRANSITION` with `{from}` and `{to}` in Spanish labels (section 7 labels). Confirming runs, in this order, the version check, the transition check, `CUSTOMER_INACTIVE`, `ORDER_EMPTY` and `INSUFFICIENT_STOCK` (with `shortages[]`), and then in one atomic step decrements the stock of every line, freezes the tax rate and the totals and sets the status. Cancelling a `confirmed` order gives every line's stock back; cancelling a `draft` changes no stock and freezes the current tax rate and the totals in the order, so a cancelled order never has an undefined rate (the seeded cancelled order has 10.00). Cancelling also voids the order's `issued` invoice once invoices exist (section 6). Shipping needs `paid`. Section 5 (Concurrency) applies: `If-Match` is optional, a stale value is 409 `VERSION_CONFLICT`, and an absent value skips the check.
- **Settings.** `tax_rate` is a string that fully matches `^[0-9]{1,3}(\.[0-9]{1,2})?$` (so `""`, `"-1"`, `" 7"`, `"1e1"`, `"10.123"` and a JSON number are `INVALID_FORMAT`; it is not trimmed), between `"0.00"` and `"100.00"` (`OUT_OF_RANGE` with the message "El valor debe estar entre 0 y 100."). It is stored with 2 decimals (`"7"` becomes `"7.00"`). Changing it does not alter confirmed orders. `DEFAULT_TAX_RATE` is the initial value.
- **List.** `page` follows the customers rule. `status` is one of the five order states (otherwise 422 `INVALID_FORMAT` on `status`). `customer_id` is an integer from 1 to 2147483647 (a non-integer is 422 `INVALID_FORMAT`, any other value is 422 `OUT_OF_RANGE`; an id that does not exist simply matches nothing). `q` has the customers rules (trimmed, ignored when empty, at most 100 characters, no control characters, literal, the same normalization) and matches the order number or the customer's name by "contains". The order is `created_at` descending, then `id` descending; `total` counts every match.
- **Not found.** An unknown id and any integer outside 1 to 2147483647 is 404 `NOT_FOUND`; an id that is not an integer is a 422 `VALIDATION_ERROR` on `id` (and `line_id` likewise). For routes with ids the order of section 7 holds: permission, existence of the order (then of the line), body validation, version and business rules.
- **Examples.** A draft with one line (the answer of `POST /api/orders/8/lines` with `{"product_id": 1, "quantity": 2, "version": 1}`, status 201, `ETag: "2"`):

  ```json
  {"id": 8, "number": "PED-0008", "status": "draft",
   "customer": {"id": 1, "name": "Acme Industrial S.A.", "status": "active"},
   "lines": [{"id": 10, "product_id": 1, "sku": "KB-100", "name": "Teclado USB",
              "quantity": 2, "unit_price": "19.90", "line_total": "39.80"}],
   "subtotal": "39.80", "tax_rate": "10.00", "tax": "3.98", "total": "43.78",
   "invoice_id": null, "version": 2,
   "created_at": "2026-11-05T15:00:00Z", "updated_at": "2026-11-05T15:01:00Z"}
  ```

  The same request with `{"product_id": 1, "quantity": 1000, "version": 2}` is a 422:

  ```json
  {"type": "about:blank", "title": "Unprocessable Content", "status": 422, "code": "VALIDATION_ERROR",
   "detail": "Revisa los datos ingresados.",
   "errors": [{"field": "quantity", "code": "OUT_OF_RANGE", "message": "El valor debe estar entre 1 y 999."}]}
  ```

- **Seed.** The 15 products and the 7 orders (with their lines, frozen totals and tax rate 10.00) of `docs/SEED.md` exist from the start, all with `version` 1 and `updated_at` equal to `created_at`; `invoice_id` is filled in by the invoices module and is `null` until it exists.

## 6. Invoices and payments (flow 3)

Invoices:
- Created manually by Finance or Admin from a `confirmed` order. Any other state returns `ORDER_NOT_INVOICEABLE`.
- The customer must have a `tax_id` (`CUSTOMER_TAX_ID_REQUIRED`).
- One invoice per order (`INVOICE_ALREADY_EXISTS`). Number `FAC-0001`, `FAC-0002`, ...
- The invoice stores a snapshot of the order lines and totals and of the customer's name, `tax_id` and address at issue time. States: `issued`, `paid`, `void`. A `paid` or `void` invoice is final.
- Issuing an invoice sends the email "Factura FAC-0001 emitida" to the customer's email through the email port (only written to the log: no real email is sent anywhere) after the transaction commits. If sending fails, the failure is logged and the invoice stays issued. No other email is sent.
- Cancelling a `confirmed` order voids its `issued` invoice.

Payments:
- Registered by Finance or Admin on an `issued` invoice (`INVOICE_NOT_PAYABLE` otherwise).
- Full payment only: the amount must equal the invoice total (`PAYMENT_AMOUNT_MISMATCH`).
- Methods: `card`, `transfer`, `cash`.

| Method | Required data |
|---|---|
| `card` | 16-digit number (spaces and hyphens are ignored) that passes the Luhn check (`CARD_NUMBER_INVALID`); an expiry in `MM/YY` format (`INVALID_FORMAT` on `card.expiry` if malformed) that is not in the past (`CARD_EXPIRED`; an expiry month is valid through its last day, using the application clock); a 3-digit CVC (`CARD_CVC_INVALID`). Only the last 4 digits are stored. |
| `transfer` | Reference of 4 to 40 characters after trimming surrounding spaces. |
| `cash` | None. |

The payment gateway is fake and replaceable. For `card`: a number ending in `0002` is declined (`reason` `CARD_DECLINED`), a number ending in `0003` finds the gateway unavailable (`reason` `GATEWAY_UNAVAILABLE`), and every other valid card is approved. `transfer` and `cash` are always approved. Fault injection can also make the gateway unavailable for any method, so every outcome is reachable by a test.

Test cards (all pass the Luhn check): `4242 4242 4242 4242` is approved, `4000 0000 0000 0002` is declined and `4000 0000 0009 0003` finds the gateway unavailable.

| Outcome | Payment | Invoice | Order |
|---|---|---|---|
| Approved | `approved` | `paid` | `paid` |
| Declined | `declined`, kept in the payment history | unchanged | unchanged |
| Gateway unavailable | `failed`, kept in the payment history | unchanged | unchanged |

Atomicity and retries:
- The order is locked first, then the invoice (section 5, Concurrency). The state is re-validated after locking and the gateway outcome is applied against that locked state.
- An approved payment, the invoice becoming `paid` and the order becoming `paid` are committed in a single database transaction.
- A declined or failed payment is committed to the payment history even though the response is an error. The error body carries `payment_id` and `reason`.
- `POST /api/invoices/{id}/payments` requires an `Idempotency-Key` header of 1 to 64 characters from `[A-Za-z0-9._-]` (missing: `IDEMPOTENCY_KEY_REQUIRED`; malformed: `VALIDATION_ERROR` with `INVALID_FORMAT` on `Idempotency-Key`).
- A key is scoped to the invoice and remembered for 24 hours. Only outcomes that created a payment row consume it: `approved`, `declined` and `failed`. A request rejected before that point (validation error, state conflict, stale `version`) does not consume the key, so a corrected retry with the same key works.
- The key is claimed atomically (a unique `(invoice_id, key)` record) before the locks are taken, and looked up again after them. Two concurrent requests with the same key and body therefore produce one payment, and the second replays the first one's response instead of failing with `INVOICE_NOT_PAYABLE`.
- Same key and same body: the stored response (status and body) is replayed, including declines and `failed` (503) outcomes. Same key and a different body: `IDEMPOTENCY_KEY_REUSED`.
- The body is compared through a keyed hash (HMAC-SHA-256 of the canonical JSON). The card number and the CVC are never stored, and the stored response contains only the last 4 digits.
- A retry after a decline or a gateway failure is a new attempt and must use a new key.
- The gateway is called while the locks are held, so injected latency is capped at 10 seconds.

| Situation | HTTP | Code | Message (es) |
|---|---|---|---|
| Order not confirmed | 409 | `ORDER_NOT_INVOICEABLE` | Solo se puede facturar un pedido confirmado. |
| Invoice already exists | 409 | `INVOICE_ALREADY_EXISTS` | Este pedido ya tiene una factura. |
| Invoice not payable | 409 | `INVOICE_NOT_PAYABLE` | Esta factura no admite pagos. |
| Amount differs from total | 422 | `PAYMENT_AMOUNT_MISMATCH` | El monto debe ser igual al total de la factura. |
| Gateway declines | 402 | `PAYMENT_DECLINED` | La pasarela rechazó el pago. Prueba con otra tarjeta. |
| Gateway unavailable | 503 | `PAYMENT_GATEWAY_UNAVAILABLE` | La pasarela de pago no está disponible. Inténtalo de nuevo. |
| Missing idempotency key | 422 | `IDEMPOTENCY_KEY_REQUIRED` | Falta la cabecera Idempotency-Key. |
| Key reused with other data | 422 | `IDEMPOTENCY_KEY_REUSED` | Esa clave de idempotencia ya se usó con otros datos. |

### Invoices and payments API

Every route needs a session. Reading is open to every role. Issuing an invoice and registering a payment need the permissions to create invoices and to register payments (Admin and Finance, section 2); anything else is 403 `FORBIDDEN`. Money is a string with 2 decimals, ids and quantities are integers, timestamps follow section 4.

| Request | Purpose | Answer |
|---|---|---|
| `GET /api/invoices` | List, with the query parameters below | 200 `{items: [InvoiceSummary], page, page_size, total}` |
| `GET /api/invoices/{id}` | Read one | 200 `Invoice` |
| `POST /api/orders/{id}/invoice` | Issue the invoice of a `confirmed` order; no body; optional `If-Match` (the version of the **order**) | 201 `Invoice`, `Location: /api/invoices/{id}` |
| `POST /api/invoices/{id}/payments` | Register a payment; `Idempotency-Key` required; optional `If-Match` (the version of the **invoice**) | 201 `PaymentResult`, or an error below |

Shapes:
- `InvoiceSummary` is `{id, number, status, order_id, order_number, customer_name, total, version, created_at, updated_at}`.
- `Invoice` is `{id, number, status, order_id, order_number, customer, lines, subtotal, tax_rate, tax, total, payments, version, created_at, updated_at}`. `customer` is the snapshot taken at issue, `{id, name, tax_id, address}` (`address` may be `null`); `lines` are the snapshot of the order lines, `{id, product_id, sku, name, quantity, unit_price, line_total}`; `subtotal`, `tax_rate`, `tax` and `total` are the order's frozen values; `payments` is the list of every attempt, ordered by `id`. Every response with one invoice carries `ETag: "<version>"`.
- `Payment` is `{id, method, status, amount, reference, card_last4, reason, created_at}`: `status` is `approved`, `declined` or `failed`; `reference` is set only for a transfer and `card_last4` only for a card (the only part of a card that is ever stored or returned); `reason` is `CARD_DECLINED` or `GATEWAY_UNAVAILABLE` for a declined or failed payment and `null` otherwise.
- `PaymentResult` is `{payment, invoice}`: the payment just created and the invoice after the payment. When the payment is approved the order is `paid` too; the screens read it again from the orders API.
- A declined payment answers 402 `PAYMENT_DECLINED` and a failed one 503 `PAYMENT_GATEWAY_UNAVAILABLE`, as problem documents with the extra members `payment_id` and `reason`; the attempt is stored and appears in `payments`.

Rules:
- **Issue.** The order must exist (404) and, under its lock and after the version check, the checks are `INVOICE_ALREADY_EXISTS`, `ORDER_NOT_INVOICEABLE` (the order is not `confirmed`) and `CUSTOMER_TAX_ID_REQUIRED` (the customer has no `tax_id`), in that order. The invoice takes the next number of the `FAC` sequence, status `issued`, `version` 1, and copies the snapshots; the order gets its `invoice_id` and its `version` increases by 1 (so a stale order version held by a screen conflicts, which is right: cancelling would now void an invoice). After the transaction commits the email "Factura FAC-0001 emitida" is sent through the email port, which only writes it to the log; a failure of the port is logged and never changes the answer.
- **Cancel.** Cancelling a `confirmed` order voids its `issued` invoice in the same transaction (`status` `void`, `version` + 1). `paid` and `void` invoices are final.
- **Register a payment.** `Idempotency-Key` is 1 to 64 characters of `[A-Za-z0-9._-]` (missing: `IDEMPOTENCY_KEY_REQUIRED`; malformed: `INVALID_FORMAT` on `Idempotency-Key`). The body is `{method, amount, card?, reference?}` with no other field. `method` is required and is `card`, `transfer` or `cash` (`REQUIRED`, `INVALID_FORMAT`). `amount` is required, a string that fully matches `^[0-9]{1,10}(\.[0-9]{1,2})?$` (`REQUIRED`, `INVALID_FORMAT`). For `card`, `card` is required and is `{number, expiry, cvc}` validated by the card rules of this section (the field paths are `card.number`, `card.expiry` and `card.cvc`); for `transfer`, `reference` is required (`REQUIRED`, then `TOO_SHORT` or `TOO_LONG`); a `card` object with another method, or a `reference` with another method, is `INVALID_FORMAT` on that field. The expiry is checked against the application clock. The checks run in the order of section 7: permission, existence of the invoice, idempotency (replay), body validation, and then under the locks the stale `version`, `INVOICE_NOT_PAYABLE` (the invoice is not `issued`), `PAYMENT_AMOUNT_MISMATCH` (422, a top-level code, when `amount` differs from the total) and the gateway. An approved payment, the invoice becoming `paid` and the order becoming `paid` (each with its `version` + 1) are one transaction.
- **Idempotency.** As described above: scoped to the invoice, 24 hours, consumed only by `approved`, `declined` and `failed` outcomes; the same key with the same body replays the stored status and body (also the 402 and 503 ones) and adds the header `Idempotency-Replayed: true`; the same key with another body is 422 `IDEMPOTENCY_KEY_REUSED`. The body is compared through `app/security/idempotency.py` (keyed hash of the canonical JSON, with the card redacted); the card number and the CVC are never stored.
- **List.** `page`, `q` and the ordering follow the orders rules. `q` matches the invoice number or the customer's name in the snapshot; `status` is `issued`, `paid` or `void` (otherwise 422 `INVALID_FORMAT`); `order_id` is an optional integer from 1 to 2147483647.
- **Examples.** Right after the seed, Finance issues the invoice of `PED-0002` with `POST /api/orders/2/invoice` (no body; status 201, `Location: /api/invoices/4`, `ETag: "1"`):

## 7. Errors and validation order

Every error is `application/problem+json` (section 8). Codes are stable; messages are Spanish and may be reworded. Authentication, rate-limit and permission errors are in sections 2 and 3; feature errors are in sections 4 to 6.

Common errors not tied to one feature:

| Situation | HTTP | Code | Message (es) |
|---|---|---|---|
| Resource does not exist | 404 | `NOT_FOUND` | No se encontró el recurso solicitado. |
| Request body above 100 KB | 413 | `PAYLOAD_TOO_LARGE` | La solicitud es demasiado grande. |
| Unexpected server error | 500 | `INTERNAL_ERROR` | Ocurrió un error inesperado. Inténtalo de nuevo. |
| Permission denied | 403 | `FORBIDDEN` | No tienes permiso para realizar esta acción. |
| Invalid body or parameters | 422 | `VALIDATION_ERROR` | Revisa los datos ingresados. |
| Order transition not allowed | 409 | `INVALID_TRANSITION` | No se puede pasar el pedido de {from} a {to}. |
| Malformed JSON body | 400 | `MALFORMED_JSON` | El cuerpo de la solicitud no es un JSON válido. |
| Lock wait above 5 seconds | 503 | `LOCK_TIMEOUT` | El recurso está ocupado. Inténtalo de nuevo. |
| All password-check slots busy for 2 seconds | 503 | `SERVICE_BUSY` | El servicio está ocupado. Inténtalo de nuevo en unos segundos. |
| Method not allowed | 405 | `METHOD_NOT_ALLOWED` | Método no permitido para este recurso. |
| Injected fault (test controls only) | 400 to 599 as configured | `INJECTED_FAULT` | Falla inyectada para pruebas. |

Field-level errors: a 422 `VALIDATION_ERROR` lists one entry per field in `errors[]`, with `field` (a path such as `lines[0].quantity`), `code` and `message`:

| Code | Message (es) |
|---|---|
| `REQUIRED` | Este campo es obligatorio. |
| `TOO_SHORT` | Debe tener al menos {min} caracteres. |
| `TOO_LONG` | Debe tener como máximo {max} caracteres. |
| `INVALID_FORMAT` | El formato no es válido. |
| `OUT_OF_RANGE` | El valor debe estar entre {min} y {max}. |
| `REFERENCE_NOT_FOUND` | El registro indicado no existe. |
| `CARD_NUMBER_INVALID` | El número de tarjeta no es válido. |
| `CARD_EXPIRED` | La tarjeta está vencida. |
| `CARD_CVC_INVALID` | El código de seguridad no es válido. |

A quantity outside 1 to 999 is `OUT_OF_RANGE`; a quantity that is not an integer is `INVALID_FORMAT`. A `customer_id` or `product_id` that does not exist is `REFERENCE_NOT_FOUND` on that field. Statuses outside this catalog render a generic Spanish message ("No se pudo completar la solicitud.") with the code derived from the status name.

Labels used in messages:

| Concept | Spanish labels |
|---|---|
| Order states | borrador, confirmado, pagado, enviado, cancelado |
| Invoice states | emitida, pagada, anulada |
| Payment states | aprobado, rechazado, fallido |
| Payment methods | tarjeta, transferencia, efectivo |
| Roles | Admin, Ventas, Finanzas, Solo lectura |

Order of checks. A request is rejected by the first rule that fails:
1. Rate limit (429) and body size (413).
2. Malformed JSON (400 `MALFORMED_JSON`).
3. Origin (403 `CSRF_ORIGIN_MISMATCH`), then session (401): the origin check is global and runs before the route's own dependencies.
4. Permission (403 `FORBIDDEN`).
5. Existence of the target resource (404 `NOT_FOUND`).
6. Idempotency: a repeated `Idempotency-Key` with the same body replays the stored response and stops here; the same key with a different body is `IDEMPOTENCY_KEY_REUSED`.
7. Body validation (422), including `IDEMPOTENCY_KEY_REQUIRED`, a malformed `Idempotency-Key` and unknown references (`REFERENCE_NOT_FOUND`).
8. Under the locks: a stale `version` (409 `VERSION_CONFLICT`), then the business rules of the operation, in this order:
   - Create or edit a customer: `CUSTOMER_EMAIL_TAKEN`.
   - Create an order: `CUSTOMER_INACTIVE`.
   - Edit a draft order: `ORDER_NOT_EDITABLE`, `CUSTOMER_INACTIVE`, `ORDER_DUPLICATE_PRODUCT`, `ORDER_TOO_MANY_LINES`.
   - Confirm, cancel or ship an order: `INVALID_TRANSITION`, then for confirm `CUSTOMER_INACTIVE`, `ORDER_EMPTY`, `INSUFFICIENT_STOCK`.
   - Create invoice: `INVOICE_ALREADY_EXISTS`, `ORDER_NOT_INVOICEABLE`, `CUSTOMER_TAX_ID_REQUIRED`.
   - Register payment: `INVOICE_NOT_PAYABLE`, `PAYMENT_AMOUNT_MISMATCH`, then the gateway (`PAYMENT_DECLINED`, `PAYMENT_GATEWAY_UNAVAILABLE`).

## 8. Formats and conventions

- **Money:** USD, stored as `NUMERIC(12,2)`, shown as `$1,234.50` (`Intl.NumberFormat('es-US', {style: 'currency', currency: 'USD'})`).
- **Dates and times:** stored and shown in UTC, never converted to the viewer's time zone, because a conversion would change the date of an invoice depending on who looks at it. Dates look like `31/10/2026` and times like `02:30`, produced with `Intl.DateTimeFormat('es-US', {day: '2-digit', month: '2-digit', year: 'numeric', timeZone: 'UTC'})` and `{hour: '2-digit', minute: '2-digit', hourCycle: 'h23', timeZone: 'UTC'}`. Timestamps in the UI carry the suffix "UTC". Without the `2-digit` options, `es-US` does not zero-pad (`3/1/2026`).
- **Errors:** RFC 9457 `application/problem+json` with `type`, `title`, `status`, `code` (stable), `detail` (Spanish) and, for validation, `errors[]` entries of `{field, code, message}`. Extension members such as `shortages`, `payment_id` and `reason` appear at the top level of the body. The UI shows the message in an element with `role="alert"`.
- **Lists:** a fixed page size of 20 (the client cannot change it), ordered by `created_at` descending and then by `id` descending, returning `items`, `page`, `page_size` and `total`. Customers are searched by name or email and orders by number or customer name, with a case- and accent-insensitive "contains" match; both accept a `status` filter.
- **Request tracing:** every response carries an `X-Request-Id` header.

Numbers continue after the seed (`PED-0008`, `FAC-0004`).

`POST /__test__/seed` takes `{"dataset": "default" | "empty"}`: `default` is the data in SEED.md and `empty` keeps only the four users and the settings.

A reset restores the data, the number sequences, the tax rate (to `DEFAULT_TAX_RATE`) and the clock offset, and clears every fault rule, the stored idempotency keys and the rate-limit counters of the instance that serves the reset (counters are per instance until they move to the database). Sessions are kept: the four users keep their ids, so a stored authentication state keeps working after a reset.

## 10. Out of scope

These are decisions, not omissions: refunds, partial payments, discounts, multiple currencies, product management screens (the catalog comes from the seed), user management, password reset, real payment gateways and real email delivery. The only email the system sends is the invoice notice in section 6.
