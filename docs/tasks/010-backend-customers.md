## Requirements

1. **Model** (`models.py`). A frozen dataclass `Customer` (`id: int`, `name`, `email`, `phone: str | None`, `tax_id: str | None`, `address: str | None`, `status: CustomerStatus`, `version: int`, `created_at: datetime`, `updated_at: datetime`), a `CustomerStatus` string enum (`active`, `inactive`), a frozen dataclass `NewCustomer` (`name`, `email`, `phone`, `tax_id`, `address`, already validated and normalized) and the type alias `Changes = Mapping[str, str | None]` whose keys are among `name`, `email`, `phone`, `tax_id`, `address`: **a key that is absent means "leave unchanged", a key whose value is `None` means "clear"**.
2. **Port** (`ports.py`), as a `Protocol` plus three exceptions (`CustomerNotFound`, `VersionConflict`, `EmailTaken`). Every method gets a docstring stating its rules, because a PostgreSQL adapter will be written from them:
   - `list(*, query: str | None, status: CustomerStatus | None, page: int, page_size: int) -> tuple[list[Customer], int]`: the page and the total number of matches, ordered by `created_at` descending then `id` descending. `query` is already trimmed and non-empty when given; it is **literal text**: `%`, `_` and `\` have no special meaning (a SQL adapter must escape them). The match is a "contains" on the search form of the name or the email, where the search form is `normalize_for_search(text)` stored at write time next to the data (a SQL adapter keeps those normalized values in columns and never relies on database collations or `unaccent`, so the semantics are identical everywhere).
   - `get(id) -> Customer | None`.
   - `add(data: NewCustomer, now) -> Customer`: **atomic**; assigns the next id, `version` 1, `created_at` and `updated_at` equal to `now` and status `active`; raises `EmailTaken` if another customer already has that (lowercase) email. A SQL adapter enforces this with a unique index and maps the violation, never with check-then-insert.
   - `update(id, changes: Changes, expected_version: int | None, now) -> Customer`: **atomic**; it locks the row first (`SELECT ... FOR UPDATE` in SQL). The checks happen in this order: `CustomerNotFound` for an unknown id; `VersionConflict` when `expected_version` is not `None` and differs from the stored version; `EmailTaken` when the new email belongs to another customer; then, if the changes leave every field as it already is, it returns the stored customer untouched (no new version, no new `updated_at`); otherwise it applies them, increases `version` by 1 and sets `updated_at = now`.
   - `set_status(id, status, expected_version, now) -> Customer`: the same rules and the same order (not found, then version conflict, then no change when the status is already the requested one). **A stale `expected_version` is a conflict even when the status already matches.**
   - `replace_all(customers: Iterable[Customer])`: replaces the whole content, for the future reset, and sets the next id to the highest id plus one (or 1 when empty).
3. **Search helper** (`search.py`): `normalize_for_search(text: str) -> str`, which applies Unicode NFKD, removes the combining marks and case-folds. This function is the normative definition of "ignoring case and accents": "Cafetería" matches "cafeteria", "ÉPSILON" matches "epsilon". The in-memory adapter compares normalized `query` against normalized name and email.
4. **Validation** (`validation.py`), plain functions that raise `ApiError(422, "VALIDATION_ERROR", "Revisa los datos ingresados.", errors=[...])` listing the problems of every field at once, with the codes and Spanish messages of SPEC section 7: `validate_new(...)` for creation (returns a `NewCustomer`) and `validate_changes(...)` for updates (returns `Changes`). Rules, all from SPEC section 4: text is trimmed; an empty optional field becomes `None`; the email is lowercased; **an empty or whitespace-only `name` or `email` is `REQUIRED`**; **each field reports only the first check that fails, in this order: required, character set or format, minimum length, maximum length**; a control character (NUL included) anywhere in a text value is `INVALID_FORMAT`; `phone` and `tax_id` accept ASCII only, as the field table says; the email has no whitespace, one `@`, a non-empty local part, a domain of at least two non-empty labels separated by dots, and at most 254 characters. For updates only the fields that were sent are validated; `None` clears `phone`, `tax_id` and `address` and is `REQUIRED` for `name` and `email`. Creation requires `name` and `email`: when they are missing the error list still includes every other problem.
5. **Service** (`service.py`): `CustomerService(repository, clock)` with `list_customers(page, query, status)`, `get(id)`, `create(data)`, `update(customer_id, data, version)`, `deactivate(customer_id, expected_version)` and `reactivate(customer_id, expected_version)`. It validates, calls the port with `clock.now()`, and translates the port exceptions into `ApiError`: `CustomerNotFound` to 404 `NOT_FOUND` ("No se encontró el recurso solicitado."), `VersionConflict` to 409 `VERSION_CONFLICT`, `EmailTaken` to 409 `CUSTOMER_EMAIL_TAKEN`, with the messages of the catalog. The service trims `query` and passes `None` when it is empty; a trimmed `query` longer than 100 characters is a 422 with `TOO_LONG` on `q`, and one with a control character is `INVALID_FORMAT` on `q`. The page size is the constant 20. A `page` outside 1 to 1,000,000 is a 422 with `OUT_OF_RANGE` on `page` and the message "El valor debe estar entre 1 y 1000000.". A `version` outside 1 to 2,147,483,647 is a 422 with `OUT_OF_RANGE` on `version` (same message pattern). An id outside 1 to 2,147,483,647 is a 404.
6. **In-memory adapter** (`adapters/memory.py`), protected by a `threading.Lock`, implementing the port. **Seed** (`seed.py`): `seed_customers()` returns the ten customers of `docs/SEED.md` (ids 1 to 10, names, emails, tax ids, statuses, phone and address of customer 1, `created_at` equal to `2026-01-01T09:00:00Z` plus `n` minutes for customer `n`, `updated_at` equal to `created_at`, `version` 1); after seeding, the next new id is 11.
7. **Schemas and routes** (`schemas.py`, `routes.py`), all **plain `def`**:
   - Pydantic models: `CustomerOut` (the `Customer` shape of the spec, status as the enum, timestamps serialized as ISO 8601 UTC with a trailing `Z`), `CustomerListOut` (`items`, `page`, `page_size`, `total`), `CustomerCreate` and `CustomerPatch`. Both input models use `extra="forbid"` (an unknown field becomes a 422 `INVALID_FORMAT` through the existing handler). **All their text fields are declared `str | None = None`, including `name` and `email` in `CustomerCreate`**, so that a missing field reaches the validation of point 4 and is reported as `REQUIRED` together with every other problem, and so that length and format problems get their own codes. `CustomerPatch` also has an integer `version` field that is required (a missing one is `REQUIRED` on `version` through the handler), and the fields that were sent are told apart from the absent ones with `model_fields_set`.
   - The six routes of the spec under `/api/customers`. **The path parameter is named `id`**, so the error field is `id`. Reading routes depend on `get_current_user`; creating, updating, deactivating and reactivating depend on `require_action(Action.MANAGE_CUSTOMERS)`. For the routes that have an id, a dependency declared **after** the permission dependency loads the customer and raises the 404, so that SPEC section 7 holds: permission, then existence (404), then body validation (422), then the version. (Dependencies that raise run before FastAPI raises the collected body errors; confirm it with the test in point 9.)
   - `POST` answers 201 with a `Location` header; every response with one customer carries `ETag: "<version>"`; `deactivate` and `reactivate` read an optional `If-Match` header (`"3"` or `3`); a malformed value is a 422 with `INVALID_FORMAT` on the field `If-Match`. Declare `responses` for 401, 403, 404, 409 and 422 with the problem shape, as the auth routes do.
   - Query parameters of the list: `page` (default 1), `q`, `status`; a `status` other than `active` or `inactive` is a 422 with `INVALID_FORMAT` on `status`.
8. **Wiring** (`main.py`): build the repository (seeded as above) and the service once, with the application clock, and store them as `app.state.customers` (the service) and `app.state.customer_repository` (the adapter, so tests and the future reset can call `replace_all`). Include the router. Add dependencies that read them from `request.app.state`.
9. **Tests** (`backend/tests/customers/`), deterministic (injected clock, no sleeps). Build the application as the auth tests do: `create_app(Settings(session_secret="test-secret", app_origin="http://localhost:3000"), clock=OffsetClock(SystemClock()))`, passing `app_origin` explicitly because `Settings()` also reads `../.env`. Because each real login costs a password hash, create **one application and one logged-in client per role for the whole module** (module-scoped fixtures) and use a function-scoped autouse fixture that calls `app.state.customer_repository.replace_all(seed_customers())` before each test. Cover:
   - `normalize_for_search`, and the validation of every field at and around its limits (name of 1, 2, 120 and 121 characters; empty and whitespace-only `name` and `email` as `REQUIRED`; email without `@`, with two `@`, without a domain dot, `a@.b`, with spaces, of 254 and 255 characters; phone and tax id character sets and lengths, non-ASCII letters rejected; address of 200 and 201 characters; a NUL character in a text field), the one-problem-per-field order (`"abc"` as a phone is `INVALID_FORMAT`, not `TOO_SHORT`), several fields reported together, trimming, empty optional fields becoming `None`, email lowercasing, and a create body with a missing `name` that also has a bad phone (both reported);
   - the adapter through contract-style tests written as test classes that take a fixture returning a fresh repository (so a PostgreSQL adapter can reuse them): ordering, pagination, `total`, search by name and by email with accents, **`q` equal to `%`, `_` and `\` matching only text that really contains them**, status filter, unique email (case-insensitive), the order of the checks in `update` (not found, then conflict, then email taken, then no-op), a no-op keeps `version` and `updated_at`, a real change bumps both, `set_status` no-op and its stale-version conflict even when the status matches, `replace_all` resetting the next id, and two threads updating the same customer with the same `expected_version` (exactly one succeeds);
   - the routes for each of the four roles (admin and sales write; finance and read-only get 403 on every write and 200 on reads; no cookie gives 401): create (201, `Location`, `ETag`, `version` 1, the `Z` suffix in the timestamps, 409 on a duplicate email, 422 listings), read (200, 404, a non-integer id as 422 on `id`, an id of 0 and of 2,147,483,648 as 404), patch (partial change, `null` clearing, `null` on `name` as `REQUIRED`, missing `version` as `REQUIRED`, `version` 0 as `OUT_OF_RANGE`, stale `version` as 409, email changing to another customer's as 409, an unknown field as 422 on that field, the no-op case, the new `ETag`), deactivate and reactivate (state change, idempotent repeat, stale `If-Match` as 409 also when the state already matches, malformed `If-Match` as 422 on `If-Match`), list (default page, page 2 after creating enough customers, an empty page beyond the last, `q` with and without accents, `q` of 101 characters, `status`, invalid `page` (`abc` as `INVALID_FORMAT`, 0 and 1,000,001 as `OUT_OF_RANGE`) and invalid `status`, ordering, `total`);
   - the order of checks of SPEC section 7 for the write routes: a wrong role with an unknown id and a bad body gives 403; an unknown id with an invalid body gives **404, not 422**; an existing id with an invalid body gives 422; an unknown id with a stale `If-Match` gives 404;
   - the OpenAPI document contains `CustomerOut` and `CustomerListOut`.
