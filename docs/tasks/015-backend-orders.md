## Requirements

1. **Models** (`models.py`): frozen dataclasses `Product` (`id`, `sku`, `name`, `price: Decimal`, `stock: int`), `OrderLine` (`id`, `product_id`, `sku`, `name`, `quantity`, `unit_price: Decimal`; `sku` and `name` are copied from the product when the line is added), `Order` (`id`, `number`, `status: OrderStatus`, `customer_id`, `lines: tuple[OrderLine, ...]`, `tax_rate: Decimal | None` (frozen at confirm; `None` while a draft), `version`, `created_at`, `updated_at`, `invoice_id: int | None`) and `Shortage` (`product_id`, `sku`, `name`, `available`, `requested`). Money is `Decimal` with 2 decimals everywhere inside; it becomes a string only in the schemas.
2. **Port** (`ports.py`): one `OrderStore` Protocol, because stock, the tax rate and the order must change in one atomic step. Exceptions: `OrderNotFound`, `LineNotFound`, `ProductNotFound`, `CustomerNotFound`, `VersionConflict`, `OrderNotEditable`, `CustomerInactive`, `DuplicateProduct`, `TooManyLines`, `InvalidTransition(from_status, to_status)` and `InsufficientStock(shortages)`. Every method has a docstring with its rules, because a PostgreSQL adapter will be written from them (state which rows it locks, in the order of SPEC section 5 "Locking": order, then customer `FOR SHARE`, then products in ascending id):
   - `list_products() -> list[Product]` ordered by id; `get_product(id) -> Product | None`.
   - `get_tax_rate() -> Decimal`; `set_tax_rate(rate: Decimal) -> None`.
   - `list_orders(*, query, status, customer_id, page, page_size) -> tuple[list[Order], int]`: `query` is already trimmed and non-empty when given, literal text, and matches the order number or the **current** name of the customer by "contains" on the `normalize_for_search` form (reuse `app/modules/customers/search.py`); ordered by `created_at` descending then `id` descending; the second value is the total number of matches.
   - `get_order(id) -> Order | None`.
   - `create_order(customer_id, now) -> Order`: atomic; raises `CustomerNotFound` or `CustomerInactive`; assigns the next number of the `PED` sequence in the same step; status `draft`, no lines, `version` 1, `tax_rate` `None`.
   - `set_customer(id, customer_id, expected_version, now)`, `add_line(id, product_id, quantity, expected_version, now)`, `set_quantity(id, line_id, quantity, expected_version, now)`, `remove_line(id, line_id, expected_version, now)`: each atomic, each returns the new `Order`, each checks in this order: `OrderNotFound`; `LineNotFound` (when a line is involved); the product or the new customer exists (`ProductNotFound`, `CustomerNotFound`); `VersionConflict` (when `expected_version` is not `None`); `OrderNotEditable`; `CustomerInactive` (the order's current customer, or the new one for `set_customer`); then `DuplicateProduct` and `TooManyLines` for `add_line`. A real change increases `version` by 1 and sets `updated_at`; changing a quantity to the same value or a customer to the same customer is a no-op that returns the stored order untouched. A new line's `id` is the next line id (one sequence for all orders).
   - `transition(id, action: OrderAction, expected_version, now) -> Order`: atomic; checks in this order `OrderNotFound`, `VersionConflict`, `InvalidTransition` (use `next_status`), then for confirm `CustomerInactive`, `ensure_confirmable` (the empty order error of the domain) and `InsufficientStock` (use `check_stock`; it carries every short line ordered by product id). Confirm decrements the stock of every line, stores the current tax rate in the order and moves it to `confirmed`; cancel of a `confirmed` order returns every line's stock, cancel of a `draft` changes no stock; ship moves `paid` to `shipped`. Every real transition increases `version` and sets `updated_at`. (The `paid` transition belongs to the payments task and is not exposed here.)
   - `replace_all(products, orders, tax_rate)`: replaces the whole content for the future reset; the next order number and line id continue after the highest existing ones.
3. **In-memory adapter** (`adapters/memory.py`): `InMemoryOrderStore(customers: CustomerRepository)`, protected by one `threading.Lock`, implementing the port; it reads the customer's status and name through the customers repository it receives (a SQL adapter will join instead). **Seed** (`seed.py`): `seed_products()` (the 15 products with the stock values of `docs/SEED.md`) and `seed_orders()` (the 7 orders with their lines, `created_at` and `updated_at` as in the seed, `version` 1, `tax_rate` `10.00` for every order that is not a draft, `invoice_id` `None`), and the initial tax rate comes from `Settings.default_tax_rate`. After seeding, the next order is `PED-0008`.
4. **Service** (`service.py`): `OrderService(store, clock, customers)` with `list_products()`, `get_tax_rate()`, `set_tax_rate(value)`, `list_orders(page, query, status, customer_id)`, `get(id)`, `create(customer_id)`, `set_customer`, `add_line`, `set_quantity`, `remove_line`, `confirm`, `cancel`, `ship`. It validates input (rules of "Orders API" in the spec: required fields, integer types, ranges, `version` bounds, unknown fields are handled by the schemas, the tax-rate format and range), calls the port with `clock.now()` and translates the port exceptions into `ApiError` with the codes and Spanish messages of the spec (`INVALID_TRANSITION` uses the Spanish state labels from `app/domain/labels.py`; `INSUFFICIENT_STOCK` carries `shortages` as an extra member and its message names the first short product). It also builds the view the routes need: the totals with `compute_totals`, using the order's frozen `tax_rate` or, for a draft, the current rate.
5. **Schemas and routes** (`schemas.py`, `routes.py`), all **plain `def`**, under `/api` exactly as the "Orders API" table says. Money fields are strings with 2 decimals (a serializer that formats the `Decimal`). Input models use `extra="forbid"`; fields whose absence or type must be reported by the validation of point 4 are declared optional (`... | None = None`) like `CustomerCreate`, except where the handler already produces the right code (a missing `version` is `REQUIRED`). The path parameters are named `id` and `line_id`. Reading routes depend on `get_current_user`; edits on `require_action(Action.EDIT_DRAFT_ORDERS)`, transitions on `TRANSITION_ORDERS`, `PATCH /api/settings` on `CHANGE_TAX_RATE`. For routes with an id, a dependency declared after the permission dependency loads the order (and the line) and raises the 404, so the order of checks of SPEC section 7 holds (permission, existence, body validation, then the version and the rules under the lock). Every response with one order carries `ETag`; creation answers 201 with `Location`; line additions answer 201. `If-Match` is parsed as in `customers/routes.py` (reuse its rule, and reject more than 10 digits before converting to an integer; do not import from the customers routes module, copy the small function or move it to a shared module only if the customers tests still pass untouched).
6. **Wiring** (`main.py`): build the store (seeded) and the service once, with the application clock and the customers repository (`app.state.customer_repository`), and keep them as `app.state.orders` and `app.state.order_store`. Include the router.
7. **Tests** (`backend/tests/orders/`), deterministic, module-scoped application and one login per role as in `tests/customers/conftest.py`, with a function-scoped autouse fixture that resets both the customers and the order store to their seeds. Cover:
   - contract-style test classes for `OrderStore` that take a fixture returning a fresh store (customers seeded): list filters and search (number, customer name with accents and `%`, `_`, `\` literal), ordering, paging, create and numbering, each edit rule in the documented order of checks, the no-op cases, duplicate product and the 11th line, transitions with the exact state table, stock decrement on confirm and return on cancel, all-or-nothing confirm with several shortages, frozen tax rate after a rate change, `replace_all`, and two threads racing: confirming the same order twice, and two orders competing for the last units of a product (exactly one wins);
   - validation: quantity at 0, 1, 999, 1000, as a string and as a float; `product_id` and `customer_id` unknown, missing and of the wrong type; `version` missing, 0, 2,147,483,648; the tax rate at `"0"`, `"0.00"`, `"100"`, `"100.01"`, `"-1"`, `"1e1"`, `"10.123"`, `10` (a number), `"7"` stored as `"7.00"`;
   - the routes for the four roles: reads for everyone; draft edits for admin and sales only; transitions for admin and sales only; the tax rate for admin only; no cookie gives 401; the state table with `INVALID_TRANSITION` message and labels; `ORDER_NOT_EDITABLE` on a confirmed order; `CUSTOMER_INACTIVE` on create, on edit and on confirm (deactivate the customer between steps); `ORDER_EMPTY`; `INSUFFICIENT_STOCK` with the `shortages` list; `VERSION_CONFLICT` with a stale body `version` and a stale `If-Match`; the rounding tie of the seed order `PED-0007` (`5.03`) and the seed totals of the 7 orders; a draft shows the current rate and a confirmed order keeps its own after the rate changes; the checks order (a wrong role with an unknown id gives 403; an unknown id with an invalid body gives 404; a known id with an invalid body gives 422; a stale version on a non-editable order gives 409 `VERSION_CONFLICT` first); `If-Match` of 5000 digits gives 422, not 500; ids at 0 and 2,147,483,648 give 404;
   - the OpenAPI document contains `Order`, `OrderSummary`, `OrderLine` and `Product`.
8. **Docs.** An "Orders" section in `backend/README.md`: the layers, what a PostgreSQL adapter must guarantee (the locking order, the atomic confirm, the number sequence), and example `curl` calls.
