# Task 018: backend PostgreSQL order store

Assignee: Worker 1. Branch: `w1/postgres-orders`. Reviewer: Supervisor.

**Base.** Branch from `main` after tasks 014 (PostgreSQL adapters) and 015 (orders backend) are merged. It uses `app/infra/db.py` (`qualified_table_name`, `unique_violation_of`, `as_utc`), the customers tables and adapter, the Alembic environment, the seed command and the integration harness of `tests/integration/`.

## Goal

The orders module runs on an in-memory store today. On the serverless deployment several function instances act at once, so orders, products, stock and the tax rate must live in PostgreSQL with the atomicity that the port documents: a confirm that cannot oversell, numbers that never repeat, no lost update, no deadlock. Add the tables and migration, the `PostgresOrderStore`, the seed and the wiring, and prove it with the same contract tests as the in-memory store plus concurrency tests. You still have no database; write the integration tests carefully, the Supervisor runs them against a real PostgreSQL and sends back what fails (this worked for the two previous tasks).

## Requirements

1. **Tables** (`app/modules/orders/tables.py`, Core `Table` objects on the shared metadata, names as given):
   - `products`: `id integer` primary key (not an identity: ids come from the seed), `sku text not null` with a unique index `products_sku_key`, `name text not null`, `price numeric(12,2) not null` with a check `price > 0`, `stock integer not null` with a check `stock >= 0`.
   - `orders`: `id integer generated by default as identity` primary key, `number text not null` with the unique index `orders_number_key`, `status text not null` with a check for the five states, `customer_id integer not null` referencing `customers(id)`, `tax_rate numeric(5,2)` nullable with a check between 0 and 100, `version integer not null`, `created_at` and `updated_at timestamptz not null`, `invoice_id integer` nullable (no foreign key yet: the invoices table does not exist), and an index `orders_created_at_id_idx` on `(created_at desc, id desc)` and one on `customer_id`.
   - `order_lines`: `id integer generated by default as identity` primary key, `order_id integer not null` referencing `orders(id)` on delete cascade, `product_id integer not null` referencing `products(id)`, `sku text not null`, `name text not null`, `quantity integer not null` with a check between 1 and 999, `unit_price numeric(12,2) not null`, a unique index `order_lines_order_product_key` on `(order_id, product_id)` (a product at most once per order), and an index on `order_id`.
   - `settings`: `key text` primary key and `value text not null`; the tax rate is the row `tax_rate`, stored as a string with two decimals.
   - The order number comes from a sequence `order_number_seq` (start 1): `nextval` inside the insert transaction. Gaps are allowed by the spec (a rolled-back transaction still consumes a number); repeats are not.
   Check constraint names are literal, and in the migration they are wrapped in `op.f(...)` (the naming convention would otherwise prefix them twice: this was found in task 012).
2. **Migration** `0002` (hand written, with a working `downgrade`) creating all of the above, and a unit test that the revision chain is `0001 -> 0002`. The downgrade drops the tables and the sequence.
3. **Adapter** (`adapters/postgres.py`): `PostgresOrderStore(engine)` implementing every method and every sentence of the docstrings of `OrderStore`. Rules that are not negotiable:
   - One transaction per method. **Lock order** (SPEC section 5): the order row (`SELECT ... FOR UPDATE`), then the customer row (`FOR SHARE`), then the product rows `FOR UPDATE` in **ascending product id**. A method that locks fewer of them takes them in that same relative order. Document the order in the module docstring.
   - The checks run **after** the locks and in the documented order, calling the domain functions (`validate_draft_lines`, `next_status`, `ensure_confirmable`, `check_stock`) and letting their `ApiError` propagate, exactly as the in-memory store does. A transition's `version` check happens after locking, never before.
   - Confirm: lock the order, the customer and every product of its lines (ascending id), check stock against the locked rows, decrement the stock, store the current tax rate (read from `settings` inside the transaction), set the status, bump `version`, all in one transaction. Cancel of a confirmed order gives the stock back (locking the same products in the same order); both cancels store the current tax rate.
   - `create_order`: one transaction; the number from the sequence; `CustomerNotFound` or `CustomerInactive` from the locked customer row.
   - `add_line`, `set_quantity`, `remove_line`, `set_customer`: lock the order, the (new) customer row and, where the port says so, check everything in the documented order; a no-op returns the stored order untouched. A violation of `order_lines_order_product_key` is a duplicate product (it can only happen if the in-transaction check was bypassed; map it to the same domain error rather than a 500).
   - `list_orders`: a join with `customers` for the current customer name; `q` matches the order number or the customer's name by "contains" on the search forms (`normalize_for_search`; for the number compare `lower()` of the number, and for the name use the customer's stored `name_search` column), literal (`autoescape=True`); `status` and `customer_id` filters; order by `created_at desc, id desc`; a separate `count(*)` with the same filters; offset and limit.
   - `get_order`: the order with its lines ordered by line id.
   - `get_tax_rate` and `set_tax_rate`: the `settings` row (`set_tax_rate` is an upsert; the value is quantized to two decimals).
   - `replace_all(products, orders, tax_rate)`: inside one transaction delete the order lines, orders and products, insert the given rows with their explicit ids, set the tax rate, and move the identity sequences and `order_number_seq` to continue after the highest existing ids and number (`setval(..., value, false)`, with 1 when empty), using schema-qualified names for any raw SQL (`qualified_table_name`).
   - Timestamps through `as_utc`; money as `Decimal` (the `Numeric` columns return `Decimal`; never go through `float`).
   - Unhandled database errors must not leak values: do not catch-and-reraise them with their message.
4. **Seed and wiring.** The `seed` command loads the 15 products, the 7 orders with their lines and the tax rate (`Settings.default_tax_rate`) only when the `products` and `orders` tables are empty, after the customers (the orders reference them), moving the sequences so the next order is `PED-0008`; running it twice changes nothing. When `settings.database_url` is set, `create_app` builds the `PostgresOrderStore` instead of the in-memory one (`app.state.order_store` keeps its name and meaning); creating the application still opens no connection.
5. **Tests.**
   - Unit: the migration chain, the table and constraint names (compile the `Table` DDL to strings as in `tests/test_tables.py`), the wiring with a bogus URL, the seed argument handling.
   - Integration (`tests/integration/`): run the existing `OrderStore` contract classes against `PostgresOrderStore` (the fixture returns a store over a freshly seeded customers table; for the in-memory store nothing changes), using the engine **without** the pinned search path, as in task 014. Add: the seed twice; every check constraint and unique index rejects what it should (negative price, stock below zero, quantity 0 and 1000, a repeated product in an order, a repeated order number, an unknown customer); the number sequence never repeats under 20 concurrent creates and continues after `replace_all`; **two threads confirming the same order** (exactly one succeeds, the other gets `INVALID_TRANSITION` or `VERSION_CONFLICT`, and the stock was decremented once); **two orders competing for the last units of a product** (exactly one confirm succeeds and the stock never goes below zero); **no deadlock**: two orders whose lines contain the same two products in opposite insertion order, confirmed at the same time from two threads, both finish (one may fail for stock, none may hang or raise a deadlock error) within a timeout; cancelling a confirmed order while another thread confirms an order of the same product leaves the stock consistent; a customer deactivated by another transaction between the lock and the check cannot slip an order past `CUSTOMER_INACTIVE` (the customer row is held `FOR SHARE`); a search with accents on the customer name, and `%`, `_` and `\` literal.
6. **Docs.** Extend the "PostgreSQL" section of `backend/README.md`: the new tables, the sequence, the lock order and the concurrency guarantees.
