# Task 019: backend invoices and payments

Assignee: Worker 1. Branch: `w1/invoices-backend`. Reviewer: Supervisor.

**Base.** Branch from `main` after tasks 015 (orders) and 017 (request guards) are merged. It uses `app/modules/orders/` (it extends it, see below), `app/modules/customers/` (read only: the invoice service receives the `CustomerRepository` to read the customer's email), `app/modules/auth/`, `app/domain/` and `app/security/idempotency.py`.

## Goal

Implement the "Invoices and payments API" subsection of `docs/SPEC.md` (flow 3): issuing an invoice from a confirmed order, the fake payment gateway, payments with idempotency, and the cancel of a confirmed order voiding its invoice. Follow the layering and the discipline of `app/modules/orders/` and of `docs/tasks/015-backend-orders.md` (port with documented atomicity, in-memory adapter as a test double, service, routes, contract-style tests a SQL adapter can reuse later, tests per role). The pure rules already exist and **must be reused**: `app/domain/payments.py` (`parse_card`, `validate_transfer_reference`, `gateway_decision`), `app/domain/numbering.py`, `app/domain/money.py`, `app/domain/labels.py` and `app/security/idempotency.py` (`validate_key`, `fingerprint`, `same_request`, `redact_card`). The production deployment is serverless with PostgreSQL, so the port is written for a future SQL adapter (task 021).

## Requirements

1. **Models** (`models.py`): frozen dataclasses `Invoice` (`id`, `number`, `status: InvoiceStatus`, `order_id`, `order_number`, the customer snapshot `customer_id`, `customer_name`, `customer_tax_id`, `customer_address`, `lines: tuple[InvoiceLine, ...]` with the copied line fields, `subtotal`, `tax_rate`, `tax`, `total` as `Decimal`, `payments: tuple[Payment, ...]` ordered by `id`, `version`, `created_at`, `updated_at`; `list_invoices` may return invoices with `lines=()` and `payments=()`, only `get_invoice`, `issue_invoice` and `register_payment` fill them), `InvoiceStatus` (`issued`, `paid`, `void`), `Payment` (`id`, `invoice_id`, `method`, `status`, `amount`, `reference`, `card_last4`, `reason`, `created_at`), `StoredResponse` (`status_code: int`, `body: dict`) for idempotency, `PaymentAttempt` (`method`, `amount: Decimal`, `card_last4: str | None`, `reference: str | None`: the validated request, never a card number or CVC) and `PaymentOutcome(response: StoredResponse, replayed: bool)` (the service builds it too for the early replay, `PaymentOutcome(stored.response, True)`; the payment and the invoice appear only as the arguments of `respond`). `StoredResponse.body` holds only JSON types: `respond` builds it with `model_dump(mode="json")`, so money is a string and timestamps are ISO strings, and it is stored as `jsonb` and replayed byte for byte. The route sets `ETag` from `response.body["invoice"]["version"]` when `status_code` is 201, and `Idempotency-Replayed: true` when `replayed`. Invoice line ids are fresh (a counter in memory, identity in SQL; the seed numbers them 1.. in table order), not the order line ids; contract tests do not compare them. Never a card number or CVC.
2. **Ports** (`ports.py`), each method documented because a PostgreSQL adapter will be written from the text:
   - `InvoiceStore`: `list_invoices(*, query, status, order_id, page, page_size) -> tuple[list[Invoice], int]`; `get_invoice(id)`; `find_key(invoice_id, key, now) -> StoredKey | None` (a plain read of a committed, not expired key of this invoice, used by the service for the early replay decision; `StoredKey(fingerprint: str, response: StoredResponse)`); `issue_invoice(order_id, expected_order_version, now) -> Invoice`; `register_payment(invoice_id, *, key, fingerprint, expected_version, attempt: PaymentAttempt, respond: Callable[[Payment, Invoice], StoredResponse], now) -> PaymentOutcome`; `void_for_order(order_id, now)`; `replace_all(invoices, payments)` (also clears the idempotency keys, restarts the number and id counters after the highest given values, and calls `link_invoices` on the order store so that every given invoice is linked to its order and no other order is). Exceptions: `InvoiceNotFound`, `OrderNotFound` (reuse the orders one), `VersionConflict`, and `ApiError`s for the business errors that the domain or the spec define (see point 4).
   - `issue_invoice` is atomic: it locks the order, then the customer (`FOR SHARE` in SQL), checks in the order of the spec (version, `INVOICE_ALREADY_EXISTS`, `ORDER_NOT_INVOICEABLE`, `CUSTOMER_TAX_ID_REQUIRED`), takes the next `FAC` number, copies the snapshots, stores the invoice and calls `attach_invoice` on the order.
   - `register_payment` is atomic and idempotent in one step: it locks the order first, then the invoice (SPEC section 5), and inside the lock (1) looks the key up (scoped to the invoice, remembered 24 hours): the same fingerprint replays the stored response and reports `replayed=True`, another fingerprint raises `IDEMPOTENCY_KEY_REUSED`; (2) otherwise checks the stale `version`, `INVOICE_NOT_PAYABLE` and `PAYMENT_AMOUNT_MISMATCH`, in that order; (3) calls the gateway (a callable of the attempt, point 3) **while the locks are held**; (4) stores the payment row (`approved`, `declined` or `failed`); (5) when approved, sets the invoice to `paid` (`version` + 1) and calls `mark_paid` on the order; (6) calls `respond(payment, invoice_after)` (a pure function of the service that renders the 201, 402 or 503 `StoredResponse`; the store cannot know the payment id before step 4) still inside the lock or transaction (the `invoice_after` argument is read again there, after step 5, with its lines and payments), stores its result with the key and returns it in the `PaymentOutcome`, **only when a payment row was created**. The first answer and every replay are rendered from a `StoredResponse` by one function of the service. A request rejected before step 4 (stale version, not payable, amount mismatch, a validation error) does not consume the key. In SQL the claim of the key is a unique `(invoice_id, key)` row inserted before the locks, so two concurrent requests with the same key give one payment and the second replays the first.
   - `void_for_order` voids the `issued` invoice of an order (`status` `void`, `version` + 1) and does nothing when there is none or when it is already final.
   - `PaymentGateway` Protocol (`gateway.py`): `charge(method: str, amount: Decimal, card_last4: str | None) -> GatewayDecision`, with a `FakeGateway` that wraps `gateway_decision`. `Mailer` Protocol (`mail.py`): `invoice_issued(to_email: str, number: str)`, with a `LoggingMailer` that writes one log line (the number only; never the address) and never raises.
2b. **Shared rules** (`rules.py`): `ensure_can_invoice(order_status, has_invoice, tax_id)` (raises, in this order, `INVOICE_ALREADY_EXISTS`, `ORDER_NOT_INVOICEABLE`, `CUSTOMER_TAX_ID_REQUIRED`), `ensure_payable(status)` (`INVOICE_NOT_PAYABLE`), `ensure_amount(amount, total)` (`PAYMENT_AMOUNT_MISMATCH`) and `totals_for(lines, rate)` (a thin use of `compute_totals`). They raise `ApiError` with the status, code and Spanish message of SPEC section 6, and have their own unit tests. The in-memory adapter calls them, and so will the PostgreSQL adapter of task 021: the codes and messages exist in exactly one place.
3. **In-memory adapter** (`adapters/memory.py`), thread-safe through the shared lock (`main.py` creates one `RLock` and gives it to the order store and to the invoice store), holding the gateway it receives. The two stores need each other: build the order store, build the invoice store with it, then set `order_store.invoices = invoice_store`. There are no rollbacks in memory: compute the new invoice and order first, then apply both (`mark_paid` before the invoice change), so an error leaves nothing half done. Because the lock is shared, a gateway call with injected latency stalls unrelated reads too; say so in the README. **Seed** (`seed.py`): `seed_invoices()` and `seed_payments()` with the exact data of `docs/SEED.md` (invoice `FAC-0001` issued for `PED-0003`, `FAC-0002` and `FAC-0003` paid, the four payments with their methods, statuses, reasons, references and `card_last4`, the fixed timestamps), and the links through `link_invoices` (`{3: 1, 4: 2, 5: 3}`, **not** `attach_invoice`: the three orders keep `version` 1 and `updated_at == created_at`); after seeding the next invoice is `FAC-0004` and the next payment id is 5. Every seeded payment's `amount` equals the total of its invoice, and the three invoices have `version` 1 and `updated_at == created_at`.
4. **Service** (`service.py`): `InvoiceService(store, orders, customers, clock, mailer, secret)` (`secret` is `settings.session_secret.encode()`; `customers` is the `CustomerRepository`) with `list_invoices`, `get`, `issue(order_id, expected_order_version)`, `pay(invoice_id, key, body, expected_version)`. `issue` calls the mailer **after** the store returns, with the email read from `customers.get(invoice.customer.id)` (a failure of the lookup or of the mailer is logged and swallowed). `pay` takes the body as received (a parsed JSON value, see point 5) and follows SPEC section 7 literally: (1) the invoice exists (404); (2) **idempotency before validation**: when the `Idempotency-Key` header is present and well formed, compute the fingerprint of the raw body with the card redacted (`redact_card` when the body is an object; any other JSON value is fingerprinted as it is) and look the key up in the store (compute the early fingerprint inside `try/except (ValueError, TypeError, RecursionError)`: `canonical_json` refuses `NaN` and `Infinity`, which Python's JSON parser accepts, a non-JSON content type can give `bytes`, and a very deep body overflows the recursion; on failure skip the early lookup, because step (3) rejects such a body with a 422; "well formed key" means that `validate_key` does not raise, and a malformed key skips the lookup and is reported in step (3)): a stored key with the same fingerprint replays, with another fingerprint it is `IDEMPOTENCY_KEY_REUSED` (so "same key, different invalid body" is `IDEMPOTENCY_KEY_REUSED`, not a 422); the in-memory store does this lookup inside `register_payment` too, the early step uses `find_key`, and `register_payment` repeats the lookup under the lock because a concurrent request may have stored the key in between; (3) otherwise validate the key (`validate_key`: missing is `IDEMPOTENCY_KEY_REQUIRED`) and the whole body, **reporting every error together**: a body that is not an object is a 422 on `body` (FastAPI itself answers `REQUIRED` on `body` for an empty or `null` body before the handler: keep that behavior and test it); a missing `Idempotency-Key` raises `IDEMPOTENCY_KEY_REQUIRED` at once, a malformed one is merged into the `errors` list; a missing `card` for the method `card` is `REQUIRED` on `card`; when a member of `card` is not a string, `parse_card` is skipped and the format errors of the other members are not reported (intended); unknown fields are `INVALID_FORMAT` on that field; `method` is required and one of `card`, `transfer`, `cash`; `amount` is required and a string that matches `re.fullmatch(r"[0-9]{1,10}(\.[0-9]{1,2})?", amount)` (never `$` or `\d`, so `"327.80\n"` and full-width digits fail); for `card`, `card` must be an object whose `number`, `expiry` and `cvc` are strings (a missing one is `REQUIRED` on `card.<name>`, a non-string or unknown one is `INVALID_FORMAT` on `card.<name>`, `card` that is not an object is `INVALID_FORMAT` on `card`), and only then `parse_card` runs with `today` from the application clock (merge its errors); for `transfer`, `reference` is required, `strip()`ped, checked with `validate_transfer_reference` and stored trimmed; a `card` with another method, or a `reference` with another method, is `INVALID_FORMAT` on that field; field names are `method`, `amount`, `card.number`, `card.expiry`, `card.cvc`, `reference`, `Idempotency-Key`; (4) call `store.register_payment` with a `respond` function that renders the stored response for each outcome (201 `PaymentResult`, 402 `PAYMENT_DECLINED` and 503 `PAYMENT_GATEWAY_UNAVAILABLE` with `payment_id` and `reason`) and return the outcome (created or replayed). The amount compared with the total is quantized to 2 decimals. Version bounds, id bounds, `q` and paging follow the orders rules (copy them; do not edit the orders service).
5. **Schemas and routes** (`schemas.py`, `routes.py`), all **plain `def`**, under `/api` exactly as the "Invoices and payments API" table says; money fields are strings with 2 decimals; input models use `extra="forbid"` and strict integers, **except the payment body**: the pay route declares its body as `Annotated[Any, Body()]` (the raw JSON), because FastAPI would validate a pydantic body before the handler and the replay must be decided before the body is validated (SPEC section 7); `PaymentCreate` exists only to document the shape in OpenAPI (through `openapi_extra`) and the service does all the validation; `POST /api/orders/{id}/invoice` is mounted by this module (the path parameter is `id`); permissions through `require_action(Action.CREATE_INVOICES)` and `REGISTER_PAYMENTS`; for routes with an id a dependency declared after the permission dependency loads the order or the invoice and raises the 404; `ETag` and `Location` as the spec says; the replay answers carry `Idempotency-Replayed: true`; the problem responses for the declined and failed payments carry the extra members `payment_id` and `reason` and the content type `application/problem+json`. `If-Match` is parsed as in the orders routes (copy the small function; more than 10 digits is rejected before converting).
6. **Order cancel** (`orders` module change b): cancelling a confirmed order voids its issued invoice in the same locked step; a test cancels an invoiced order and reads the invoice as `void`.
7. **Wiring** (`main.py`): build the invoice store, the service and the router **only when `database_engine is None`** (task 021 wires the PostgreSQL case; with `DATABASE_URL` set this task wires nothing for invoices, because `PostgresOrderStore` has no `link_invoices`, `attach_invoice` or `mark_paid` yet).
