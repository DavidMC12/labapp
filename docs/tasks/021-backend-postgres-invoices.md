# Task 021: backend PostgreSQL invoice store

Assignee: Worker 1. Branch: `w1/postgres-invoices`. Reviewer: Supervisor.

**Base.** Branch from `main` after tasks 018 (PostgreSQL order store) and 019 (invoices and payments) are merged. Read `docs/tasks/018-backend-postgres-orders.md` and `docs/tasks/019-backend-invoices-payments.md` first: this task is the PostgreSQL adapter of the port written in 019, built the way 018 built the order store, and it completes two operations that cross the two modules.

## Goal

Make invoices, payments and idempotency keys live in PostgreSQL with the atomicity that the `InvoiceStore` port documents, so that on the serverless deployment two instances cannot pay one invoice twice, replay a payment wrongly or leave an invoice `paid` with an order that is not. You still have no database: the Supervisor runs the integration tests against a real PostgreSQL and sends back what fails. Write the concurrency tests with threads and short timeouts so a deadlock fails fast.

## Requirements

1. **Tables** (`app/modules/invoices/tables.py`, names as given; check constraint names in the migration wrapped in `op.f(...)`):
   - `invoices`: `id integer generated by default as identity` primary key, `number text not null` with the unique index `invoices_number_key`, `status text not null` check (`issued`, `paid`, `void`), `order_id integer not null` referencing `orders(id)` with the unique index `invoices_order_key` (one invoice per order), the customer snapshot `customer_id integer not null`, `customer_name text not null`, `customer_tax_id text not null`, `customer_address text`, `subtotal`, `tax` and `total` as `numeric(12,2) not null`, `tax_rate numeric(5,2) not null`, `version integer not null`, `created_at` and `updated_at timestamptz not null`, an index `invoices_created_at_id_idx` on `(created_at desc, id desc)`.
   - `invoice_lines`: `id integer generated by default as identity` primary key, `invoice_id integer not null` referencing `invoices(id)` on delete cascade, `product_id integer not null`, `sku`, `name`, `quantity integer not null`, `unit_price numeric(12,2) not null`.
   - `payments`: `id integer generated by default as identity` primary key, `invoice_id integer not null` referencing `invoices(id)`, `method text not null` check (`card`, `transfer`, `cash`), `status text not null` check (`approved`, `declined`, `failed`), `amount numeric(12,2) not null`, `reference text`, `card_last4 text` with a check that it is four digits when present, `reason text`, `created_at timestamptz not null`, an index on `invoice_id`.
   - `idempotency_keys`: `invoice_id integer not null` referencing `invoices(id)`, `key text not null`, `fingerprint text not null`, `status_code integer not null`, `response jsonb not null`, `created_at timestamptz not null`, primary key `(invoice_id, key)`.
   - The invoice number comes from the sequence `invoice_number_seq` (start 1); gaps are allowed, repeats are not. `orders.invoice_id` gets its foreign key to `invoices(id)` in this migration (nullable).
2. **Migration** `0003` (hand written, with a working `downgrade`), and a unit test that the chain is `0001 -> 0002 -> 0003`.
3. **Adapter** (`adapters/postgres.py`): `PostgresInvoiceStore(engine, gateway)` implementing every method of the port and every sentence of its docstrings. Not negotiable:
   - One transaction per method. **Lock order** (SPEC section 5): the order row (`FOR UPDATE`), then the invoice row (`FOR UPDATE`), then the customer row (`FOR SHARE`) when the customer is needed. Document it in the module docstring. The checks run **after** the locks and in the documented order; the domain's `ApiError`s propagate unchanged.
   - `issue_invoice`: lock the order and the customer; checks in order (version, `INVOICE_ALREADY_EXISTS`, `ORDER_NOT_INVOICEABLE`, `CUSTOMER_TAX_ID_REQUIRED`); `nextval` of the sequence; insert the invoice and its line snapshot; set the order's `invoice_id` and bump its version. A violation of `invoices_order_key` (a concurrent issue that slipped past the lock) maps to `INVOICE_ALREADY_EXISTS`.
   - `register_payment`: in one transaction: (a) **claim the key first, before any lock**: delete an expired row of this `(invoice_id, key)` (older than 24 hours with the injected clock), then `INSERT ... ON CONFLICT DO NOTHING`; when the insert did nothing, read the existing row: the same fingerprint replays its stored status and body, another fingerprint is `IDEMPOTENCY_KEY_REUSED` (a concurrent claimant that has not committed makes the insert wait, so the second request sees the committed row); (b) lock the order, then the invoice; (c) check the stale `version`, `INVOICE_NOT_PAYABLE` and `PAYMENT_AMOUNT_MISMATCH`, in that order, raising their `ApiError`: the raise rolls the whole transaction back, **including the claim, so a rejected request does not consume the key**; (d) call the gateway while the locks are held; (e) insert the payment row; (f) when approved, set the invoice `paid` (version + 1) and mark the order `paid` (version + 1); (g) store the response of the caller in the claim row (`status_code`, `response`) and commit, for approved, declined and failed outcomes alike (a declined or failed attempt **commits** the payment and the key and the method returns an outcome, it does not raise).
   - `void_for_order`, `list_invoices` (join-free: the snapshot holds the customer name; `q` matches the number or the snapshot name by "contains" on the search form, literal), `get_invoice` (with its lines and its payments ordered by id), `replace_all(invoices, payments)` (inside one transaction: delete payments, keys, invoice lines and invoices, insert the given rows with explicit ids, move the sequences with schema-qualified raw SQL as in task 018).
   - Timestamps through `as_utc`; money as `Decimal`; the card number and CVC never reach this layer (only `card_last4`); unhandled database errors are not caught and re-raised with their message.
4. **Order store completion** (`orders/adapters/postgres.py`): implement `attach_invoice` and `mark_paid` as the port says (one transaction, lock the order row, bump the version), and make `transition(cancel)` of a `confirmed` order void its `issued` invoice (`status` `void`, `version` + 1) **in the same transaction**, after locking the order and before the stock is returned, with the invoice row locked after the order row.
5. **Seed and wiring.** The `seed` command loads the 3 invoices, their lines, the 4 payments and `attach_invoice` for the three orders, only when `invoices` is empty and after the orders; the sequences continue (`FAC-0004`, payment id 5); idempotent. When `settings.database_url` is set, `create_app` builds the PostgreSQL invoice store (same names on `app.state`); no connection at startup.
6. **Tests.**
   - Unit: the migration chain, the table and constraint names (compile the DDL to strings), the wiring, the seed argument handling.
   - Integration: run the existing `InvoiceStore` contract classes against the PostgreSQL store with the engine **without** the pinned search path, plus: the seed twice; the constraints (a second invoice for an order, a repeated number, a bad status, `card_last4` with letters, a payment with an unknown method); **two threads paying one invoice with the same key and body** (one payment row, one replay with the same body, the gateway called once); **two threads with different keys** (exactly one approval, the other `INVOICE_NOT_PAYABLE`); a key claimed by a request that is then rejected (stale version, amount mismatch) is free again; a declined attempt keeps its key and replays as a 402; the 24-hour expiry; **pay and cancel racing on the same confirmed order** (both finish within a timeout, no deadlock, and the final states are consistent: either paid and not cancellable, or void and not payable); two concurrent issues for one order (one wins, the other gets `INVOICE_ALREADY_EXISTS`); issue racing with a customer deactivation or a `tax_id` change (the `FOR SHARE` lock makes the snapshot consistent); the snapshot stays unchanged after the customer changes; a search with accents; the number sequence never repeats under 20 concurrent issues.
7. **Docs.** Extend the "PostgreSQL" section of `backend/README.md`: the new tables, the sequence, the lock order, the key claim and the guarantees.
