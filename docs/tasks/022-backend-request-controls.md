## Requirements

1. **Tables and migration** `0004` (hand written, with a working `downgrade`, check names in `op.f(...)`): `fault_rules` with `id integer generated by default as identity` primary key, `target text not null` check (`route`, `gateway`), `method text` nullable check (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`), `path text` nullable, `latency_ms integer not null default 0` check between 0 and 10000, `status integer` nullable check between 400 and 599, `remaining integer` nullable check `>= 0` (null means until removed; a rule at 0 is exhausted and ignored by every read), `created_at timestamptz not null`. The same migration **inserts** the `settings` row `clock_offset_seconds` with the value `'0'` (a string with the number). Unit test of the chain `0003 -> 0004` and of the constraint names.
2. **Clock.** A `ClockOffsetStore` Protocol (`get() -> float`, `set(seconds: float)`, `advance(seconds: float) -> float`) with an in-memory implementation (backed by the existing `OffsetClock`, which keeps working unchanged for the in-memory mode and the existing tests) and a PostgreSQL one (the `settings` row; `advance` is a single `UPDATE settings SET value = (value::float8 + :delta)::text WHERE key = 'clock_offset_seconds' RETURNING value`, so two concurrent advances never lose one; `set` is an upsert). The application clock reads the offset **once per request**, through the request-controls middleware of point 4: it stores the loaded value in a `contextvars.ContextVar`, and `now()` adds it to the system time; outside a request (the CLI) `now()` reads the store directly. A request that changes the offset sees the new value at its own next call.
3. **Faults.** A `FaultStore` Protocol with a documented atomicity contract and two implementations (in memory, thread-safe; PostgreSQL): `add(rule) -> Rule` (at most 50 non-exhausted rules; the check and the insert are one statement or happen under a transaction advisory lock, so two concurrent adds cannot both pass at 49; adding also deletes the exhausted rows), `list()` (non-exhausted rules, by id), `clear()`, `take(method, path) -> FaultDecision | None` and `take_gateway() -> FaultDecision | None`. `take` finds the first rule (by id) of target `route` whose method (or none) and exact path match and that is not exhausted; `take_gateway` the first non-exhausted rule of target `gateway`. Both **consume atomically** with a single statement of this shape: `UPDATE fault_rules SET remaining = CASE WHEN remaining IS NULL THEN NULL ELSE remaining - 1 END WHERE id = (SELECT id FROM fault_rules WHERE <match> AND (remaining IS NULL OR remaining > 0) ORDER BY id LIMIT 1 FOR UPDATE) RETURNING latency_ms, status`. Under N concurrent matching requests exactly `remaining` of them get a decision (the others, after waiting for the row lock, re-check the condition and get none). A rule is a `Rule(id, target, method, path, latency_ms, status, remaining)`; a `FaultDecision` is `(latency_ms, status)`.
   - **Gateway.** Wrap the gateway of the invoices module in a `FaultyGateway(inner, store, sleep)` (in `gateway.py`) that, when `take_gateway()` returns a decision, waits its latency (capped at 10 seconds, `sleep` injectable) and answers `unavailable` with the reason `GATEWAY_UNAVAILABLE` without calling the inner gateway; with no decision it calls the inner gateway. A gateway rule needs no `status` (it must be absent) and no `latency_ms`: `{"target": "gateway", "times": 1}` is valid.
   - **Rule validation** (a function in the module, used by task 024): for `route`, `path` is required, starts with `/` and is matched exactly, and the rule needs a latency above 0 or a status; for `gateway`, `method`, `path` and `status` must be absent.
4. **Request controls middleware** (pure ASGI, `app/guards/request_controls.py`). For every HTTP request except the ones under `/__test__/` and `GET /api/health`, and **only when the application has controls enabled** (`test_mode` is on or `test_token` is non-empty; otherwise it does nothing at all), it loads in **one connection** (one `run_in_threadpool` call, never a synchronous database call inside the event loop) the clock offset and the matching fault decision (`take`), puts the offset in the `ContextVar`, waits the latency (`asyncio.sleep`, injectable for tests) and, when the decision has a `status`, answers a problem document with that status, the code `INJECTED_FAULT` and the detail "Falla inyectada para pruebas." without calling the application. In memory-only mode the same code path runs against the in-memory stores without a thread hop. Creating the application and `GET /api/health` open no connection (the existing test in `tests/test_wiring.py` must keep passing). Middleware order, outside to inside: request id, rate limit, controls guard, **request controls**, body size, application (`add_middleware` wraps, so the last one added is the outermost; write the registration with a comment saying so).
5. **Config.** `Settings` refuses to start when `test_mode` is on and the environment says it is a Vercel deployment (`VERCEL_ENV` is `production` or `preview`): `TEST_MODE=1` online would open every control and rate limits to anyone. Unit test.
6. **Wiring** (`main.py`): choose the in-memory or the PostgreSQL stores by `settings.database_url`; keep `app.state.clock_store` and `app.state.fault_store`; the invoice service receives the `FaultyGateway`; creating the application opens no connection.
7. **Tests.** Unit (in memory): the rule validation table, the `take` matching (method, path, exact match, first by id), the `times` countdown to exhaustion, the middleware (enabled and disabled, exemptions for health and `/__test__/*`, latency with an injected sleep, status, no work without controls), the effect of the clock on `SESSION_EXPIRED` through the real login and `GET /api/auth/me` routes (set the offset in the store, call, advance past eight hours, call again), the gateway rule through a real payment (`PAYMENT_GATEWAY_UNAVAILABLE`, payment stored as `failed`, consumed after one use), the `Settings` refusal. Integration (PostgreSQL, two applications built with the same database to play two instances): an offset set through instance A is seen by instance B's next request; a fault added through A applies on B; **N concurrent requests against a rule with `times` equal to K get exactly K injected failures**; two concurrent `advance` calls add up; two concurrent adds at 49 rules leave at most 50; a gateway rule consumed once by two concurrent payments to two invoices is used by exactly one of them.
8. **Docs.** A "Request controls" section in `backend/README.md`: what is stored where, the middleware order, the cost (one extra connection per request, only when controls are enabled) and the limits.
