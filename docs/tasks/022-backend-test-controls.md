# Task 022: backend test-only controls with state in PostgreSQL

Assignee: Worker 1. Branch: `w1/test-controls`. Reviewer: Supervisor, with a second-agent review because this is security-sensitive code.

**Base.** Branch from `main` after tasks 017, 018, 019 and 021 are merged. It uses the guards of `app/guards/` (the controls middleware already answers 404 to every request under `/__test__` without the token), `app/infra/clock.py`, every adapter and seed of the other modules, and the integration harness.

## Goal

Build the test-only controls of `docs/ARCHITECTURE.md` ("Test-only controls") and SPEC sections 3 and 9: `POST /__test__/reset`, `POST /__test__/seed`, `GET` and `POST /__test__/clock`, and `POST`, `GET` and `DELETE /__test__/faults`, with the fault injection they feed. They exist so that the owner's automated tests (which run against deployments on a serverless platform) can restore a known state, move the application's time and provoke latency and failures. Because several function instances serve requests and none lives between requests, **every piece of state lives in PostgreSQL** (the clock offset, the fault rules, the data) and is read by every instance; in-memory mode (no `DATABASE_URL`) keeps working through the in-memory stores and is the test double of this task.

## Requirements

1. **Tables and migration** `0004` (hand written, with a working `downgrade`, check names in `op.f(...)`): `fault_rules` with `id integer generated by default as identity` primary key, `target text not null` check (`route`, `gateway`), `method text` nullable check (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`), `path text` nullable, `latency_ms integer not null default 0` check between 0 and 10000, `status integer` nullable check between 400 and 599, `remaining integer` nullable check `> 0`, `created_at timestamptz not null`; and the `settings` row `clock_offset_seconds` (a string with the number; absent means 0). Unit test of the chain `0003 -> 0004` and of the constraint names.
2. **Clock.** A `ClockOffsetStore` Protocol (`get() -> float`, `set(seconds: float)`) with an in-memory implementation (backed by the existing `OffsetClock`) and a PostgreSQL one (the `settings` row). The application clock reads the offset **once per request**: a pure ASGI middleware loads it from the store at the start of each request into a `contextvars.ContextVar`, and `now()` adds that value to the system time (outside a request, for example in the CLI, it reads the store directly). The middleware does nothing when no database is configured. A request that changes the offset sees the new value at its own next call. Keep `OffsetClock` working unchanged for the in-memory mode and the existing tests.
3. **Faults.** A `FaultStore` Protocol with a documented atomicity contract and two implementations (in memory, thread-safe; PostgreSQL): `add(rule) -> Rule`, `list()`, `clear()`, and `take(method, path) -> FaultDecision | None`, which finds the first rule (by id) of target `route` whose method (or none) and exact path match, **decrements `remaining` atomically** (a single `UPDATE ... RETURNING`, deleting the rule when it reaches zero; `remaining` null means until removed) and returns the latency and status to apply; under N concurrent matching requests exactly `remaining` of them get a decision. A `gateway` rule is read by the payment gateway: wrap the gateway of the invoices module in a `FaultyGateway` that, when a `gateway` rule is present, waits its latency (capped at 10 seconds) and answers `unavailable` with the reason `GATEWAY_UNAVAILABLE`, consuming the rule the same way. A fault middleware (pure ASGI, in `app/guards/`) calls `take` for every request except the ones under `/__test__/` and `GET /api/health`, waits the latency (`asyncio.sleep`, injectable for tests) and, when the rule has a `status`, answers a problem document with that status, the code `INJECTED_FAULT` and the detail "Falla inyectada para pruebas." without calling the application. Middleware order, outside to inside: request id, rate limit, controls guard, **clock offset, fault injection**, body size, application (and remember that `add_middleware` wraps, so the last added is the outermost). In memory-only mode with no rules the fault middleware does no work.
4. **Reset and seed.** A `Resetter` that restores, as SPEC section 9 says: the data of every module (customers, products, orders with their lines, invoices with their lines and payments, idempotency keys), the number sequences (the next order is `PED-0008`, the next invoice `FAC-0004`, the next payment id 5, the next customer id 11), the tax rate (to `Settings.default_tax_rate` quantized), the clock offset (to 0), the fault rules (removed), the rate-limit counters (the in-memory limiters of the instance; shared limits are a later task) and **keeps the sessions**: the four users keep their ids (upsert and delete-missing, never touching sessions). In PostgreSQL the whole reset is **one transaction** (`engine.begin()` and the `connection=` keyword of point "Scope"), so no request can see a half-restored database, and it takes an advisory lock so two resets do not interleave; the deletion order respects the foreign keys (payments, keys, invoice lines, invoices, order lines, orders, customers, products) and the insertion order is the reverse. `seed(dataset)` with `default` is the same data as the reset (without touching the clock, the faults or the counters) and with `empty` leaves only the four users and the settings (every other table emptied, sequences restarted, the tax rate restored).
5. **Router** (`app/modules/testcontrols/`), mounted at `/__test__` (not under `/api`), `include_in_schema=False`, all plain `def` handlers, JSON bodies with `extra="forbid"` and strict types:
   - `POST /__test__/reset` answers 200 `{"status": "ok"}`.
   - `POST /__test__/seed` takes `{"dataset": "default" | "empty"}` (any other value is a 422 `VALIDATION_ERROR` on `dataset`) and answers 200 `{"dataset": "<value>"}`.
   - `GET /__test__/clock` answers `{"now": "<ISO 8601 UTC with Z>", "offset_seconds": <number>}`; `POST /__test__/clock` takes exactly one of `{"offset_seconds": number}` (replace) or `{"advance_seconds": number}` (add; read and write in one transaction, `SELECT ... FOR UPDATE` on the settings row in SQL); anything else, a non-finite number, an offset beyond plus or minus ten years, is a 422; the answer has the same shape as the `GET`.
   - `POST /__test__/faults` adds a rule and answers 201 with the rule and its `id`. Body: `{"target": "route" | "gateway", "method": "GET" | "POST" | "PUT" | "PATCH" | "DELETE" | null, "path": string | null, "latency_ms": integer 0 to 10000 (default 0), "status": integer 400 to 599 | null, "times": integer 1 to 1000 | null}`. For `route`, `path` is required, starts with `/` and is matched exactly; for `gateway`, `path` and `method` must be absent; a rule with neither latency nor status is a 422. `GET /__test__/faults` lists the rules (with the remaining count); `DELETE /__test__/faults` removes all of them (204). At most 50 rules exist at once (a 422 beyond).
   The guard of task 017 stays in front of everything; this router adds no authorization of its own and must not be reachable without it (a test that builds the application with a token and without one proves it).
6. **Wiring** (`main.py`, `container.py`): choose the in-memory or the PostgreSQL implementations by `settings.database_url`; keep `app.state.fault_store`, `app.state.clock_store` and `app.state.resetter`; creating the application and the health check open no connection. The CLI gets `reset` (a plain call to the resetter, for local use).
7. **Tests.** Unit (in memory): every endpoint and every validation (bodies at their boundaries, unknown fields, the two clock bodies, non-finite numbers, the faults rules table), the guard (with and without the token, `TEST_MODE` 0 and 1), the effect of the clock on `SESSION_EXPIRED` through the real login and `GET /api/auth/me` routes (set the offset, call, advance past eight hours, call again), fault latency (with an injected sleep) and status, the `times` countdown, method and path matching, exemptions for health and `/__test__/*`, the gateway rule through a real payment (the payment fails with `PAYMENT_GATEWAY_UNAVAILABLE`), reset (modify a customer, an order, an invoice, the rate, the clock, add a fault, log in; reset; everything is back, the session still works), seed `empty` and `default`. Integration (PostgreSQL, two applications created with the same database to play two instances): an offset set through instance A is seen by instance B's next request; a fault added through A applies on B; **N concurrent requests against a rule with `times` equal to K get exactly K injected failures**; the reset is atomic (a reader thread polling the customers count during a reset only ever sees the old or the new total, never a mix) and keeps the sessions; the sequences restart; reset twice in a row is idempotent; two concurrent resets both finish; `seed` empty then an order creation gives `PED-0001`.
8. **Docs.** A "Test controls" section in `backend/README.md`: each endpoint with an example `curl`, the guard table, what is stored where, what a reset keeps, the middleware order, and the note that the shared rate-limit counters are a later task.
