# Task 059: the customers import screen

Assignee: Worker 2. Branch: `w2/customers-import-ui`. Reviewer: Supervisor.

**Base.** Branch from `main` after task 058 (the backend import) is merged (the supervisor tells you); until then branch from `w1/customers-import`.

## Goal

The API now creates customers from an uploaded CSV file, all or nothing (`POST /api/customers/import`, the **Import** rule of `docs/SPEC.md` section 4). Add the screen: a page with a native file input, a submit button, a clear success message and a table that lists every row error of a rejected file. File upload with a good and a bad file is one of the exercises a test engineer practices, so the screen must be plain, observable and accessible.

## Read first

`docs/SPEC.md` (the **Import** rule: every error shape is there, with the field names `file`, `rows[N]` and `rows[N].<column>`), `docs/TESTABILITY.md` (the id grammar, `data-state`, `aria-busy`), `docs/TESTIDS.md`, `frontend/src/app/(app)/customers/new/page.tsx` and `frontend/src/features/customers/` (how the create form validates, shows server errors, moves focus to its alert and disables the submit button while sending; the API client and how it reads a problem body), `frontend/src/lib/` (the request helper: look at how it sets headers and whether it can send a `FormData` body: the browser must set the multipart `Content-Type` itself, so that header must not be forced), `frontend/src/app/(app)/customers/page.tsx` (the permission gating of the "Nuevo cliente" link), the UI components of `frontend/src/components/ui/`, `tools/audit/README.md`.

## Scope

You may edit under `frontend/` (the new page `src/app/(app)/customers/import/page.tsx`, a new feature module or additions to `src/features/customers/`, the customers list page for the link, the tests, the README), `tools/audit/states.json` (by text: add lines, keep the existing ones byte-identical), `docs/TESTIDS.md` (regenerated), `tools/audit/README.md` (one sentence). No new dependency. Do not change an existing `data-testid` or text. Do not duplicate the validation rules of the API: the server is the only judge of a file.

## Requirements

1. **The link.** On the customers list, next to "Nuevo cliente" and gated the same way (Admin and Sales only), a link "Importar CSV" with the id `customers-list-import-link` to `/customers/import` (a client-side navigation is fine here).
2. **The page** `/customers/import`, title "Importar clientes" through the existing title hook, the heading `customers-import-heading`; a help paragraph `customers-import-help-text` that says in Spanish: the file is a CSV in UTF-8 with a header row; the columns are `name` and `email` (required) and `phone`, `tax_id`, `address` (optional); at most 200 rows and about 100 KB; if any row is wrong nothing is imported. A native `<input type="file" accept=".csv,text/csv">` with a visible `<label>` "Archivo CSV" (id `customers-import-file-input`, the label associated, the help paragraph referenced by `aria-describedby`), a submit button "Importar" (`customers-import-submit-button`), disabled until a file is chosen and while sending, and a link "Volver a clientes" (`customers-import-back-link`). The form has the id `customers-import-form`. Users without the permission get the same "no permission" treatment as the create page (read how it is done), never the form.
3. **Sending.** One `fetch` of `POST /api/customers/import` with a `FormData` that holds the file under the name `file` (same origin, session cookie, no JSON `Content-Type`). While it is in flight: `aria-busy="true"` on the form, the button disabled, `data-state="loading"` on the form (`idle`, `loading`, `success`, `error` are the states, as the other forms do). A network failure shows a generic alert like the other screens do.
4. **Success (201).** A `role="status"` element `customers-import-result-text` says "Se importaron N clientes." (singular for 1: "Se importó 1 cliente."), the form goes back to `idle`, the file input is cleared and the submit button disabled again, and a link "Ver clientes" (`customers-import-list-link`) to `/customers`. The customers list must show the new customers afterwards (the list's cached queries are invalidated).
5. **Rejection (422).** A `role="alert"` element `customers-import-error-alert` (focus moves to it, as the create form does) says "El archivo tiene errores. No se importó nada." and, under it, a table `customers-import-errors-table` inside the app's `TableScroll`, with the columns "Línea", "Campo" and "Mensaje", one row per entry of `errors[]` in the order the API sends them, row ids `customers-import-error-row-N` (N from 1) and cell ids `customers-import-error-line-N`, `customers-import-error-field-N`, `customers-import-error-message-N`. The line is the `N` of `rows[N]` or `rows[N].<column>` (a whole-file error has no line: show "—"); the field is the Spanish label of the column (`name` Nombre, `email` Email, `phone` Teléfono, `tax_id` ID fiscal, `address` Dirección; `file` shows "Archivo"; `rows[N]` with no column shows "Fila completa"); the message is the API's message. When the API sends exactly 100 entries, add a paragraph `customers-import-truncated-text`: "Se muestran los primeros 100 errores." The result text of an earlier success is cleared when a new attempt starts.
6. **Other answers.** 413 shows an alert "El archivo es demasiado grande (máximo 100 KB)." in the same alert element; 409 `CUSTOMER_EMAIL_TAKEN` and 403 show the API's own message there; any other failure shows the generic message the other screens use.
7. **Accessibility and look.** The ledger look of the app (inputs, buttons and the table use the existing components and tokens), visible focus, the page works at 320 px (the audit checks it), light and dark themes, no color-only information.
8. **Tests** (Vitest and Testing Library, `fetch` mocked): the page renders its elements and ids; the button is disabled until a file is chosen (use `userEvent.upload`); the `FormData` of the request holds the file under `file` and the `Content-Type` header is not set by the code; loading state; the success text in singular and plural and the cleared input; the 422 table with whole-file, row and column errors (the three label mappings), the line numbers, the order, the "—", the truncation note at exactly 100; 413, 409, 403 and a network failure; focus moves to the alert; the list link appears for Admin and Sales and not for Finance or Read-only; the cached list is invalidated after a success.
9. **The audit.** Add to `tools/audit/states.json`: `customers-import` (`/customers/import`, user `sales@labapp.test`, `waitFor` `customers-import-form`, title "Importar clientes · LabApp"), `customers-import-narrow` (the same at 320 by 568, `"catalog": false`) and `customers-import-readonly` (user `readonly@labapp.test`, `waitFor` the id of the no-permission element, `"catalog": false`). Run the browser audit in both themes (`tools/audit/README.md`, in-memory API with `DATABASE_URL= DATABASE_URL_UNPOOLED= scripts/dev.sh`): all states pass. Regenerate `docs/TESTIDS.md` against a clean seed as the README says and commit it.
10. **Check it with a real browser and a real file.** With the dev servers running, drive the page with Chromium over the DevTools protocol (the audit shows how the project does it; `DOM.setFileInputFiles` sets a file on the input): upload a good file of three rows and confirm the result text, that the customers list now has them and the ids; upload a file with a bad row, a repeated email and a short row and confirm the error table (lines, labels and messages) and that no customer was created; upload a file named `datos.txt` and one of 120 KB and confirm the messages. Put the observed texts in the report. Keep the sample files outside the repository.
11. **README.** `frontend/README.md`: a short "Customers import" paragraph (the ids and the states).
